# cognee-ingestion

Data ingestion pipeline for cognee (the `add` stage) — streams input, computes content hashes, and persists data plus metadata with multi-tenant isolation.

`data` rows are dataset-scoped, as in Python (`ingest_data.py`): a new row gets a random `uuid4` id and its dataset in `data.dataset_id`; re-adding content reuses the row that holds the same `content_hash` in the same dataset for the same owner and tenant (Python's `identify_many`). The same content in another dataset is another row. Dataset ids are deterministic (`generate_dataset_id`: UUID5 of name, owner and tenant).

Loaders run at `add`, as in Python (`ingest_data.py`, `loaders/store_derived_text.py`): the stored file is the extracted text `text_<content_hash>.txt` (`extension` `txt`, `mime_type` `text/plain`, `raw_content_hash` its MD5), and `original_data_location` keeps the source. `AddPipeline` uses `LoaderRegistry::default_registry()` (text, HTML, PDF, CSV, unstructured) unless `with_loader_registry` gives it another. The image and audio loaders need an LLM or a transcriber, so they are registered with `LoaderRegistry::register_image_loader` / `register_audio_loader`; the CLI and the bindings pass `ComponentManager::add_loader_registry()`, which has both whenever the configured LLM provides them. An image is then stored as its vision-LLM description and an audio file as its Whisper transcript. Without them an image or audio input fails with `UnsupportedDocumentType`.

Directories are resolved before anything is stored (`code_repo`, Python's `resolve_data_directories` and `code_repo.py`). A code project (a directory whose root has a project marker such as `pyproject.toml`, `go.mod` or `.git`) becomes one repo manifest item, stamped `system_metadata.source = "code_repo"` for cognify's CODE_REPO route, plus its document files; hidden files, build directories, binaries, media, symlinks and Git LFS pointers are skipped. Without an LLM (`AddPipeline::with_llm_available(false)`) the documents are skipped too. Any other directory is added file by file. The manifest text and the route stamp are byte-identical to Python's, and the manifest's data id is pinned to `(user, dataset, repo path)` as Python's `get_unique_data_id` derives it (`code_repo::code_repo_data_id`), so re-adding a repository updates its one row (a changed one loses its cognify marker and is cognified again). Hidden and build directories are not walked, and an unreadable subdirectory or file is skipped with a warning. `AddPipeline::add_code_repository` stores a repository as its one manifest item without its documents (Python's `add_code_repository`, for `remember(content_type="code")`).

Remote repositories (`resolve_repo`, Python's `resolve_repo.py`): a GitHub/GitLab repository URL given to `add` (`code_repo_clone_url`) is shallow-cloned and resolved like a local code project, its manifest recording the credential-free `repo_url` and pinned to the default branch's clone, so every branch of a URL (`AddParams::branch`) shares one row. `resolve_repo_source` also serves `remember(content_type="code")`. Clones live under `AddPipeline::with_repo_sources` (`code_graph.clones_dir`, default `~/.cognee/repos`), one directory per URL and branch, and are refreshed best-effort. Remote repositories follow Python's `ALLOW_HTTP_REQUESTS` gate (fail-closed when nothing is configured) and an http(s) host may not be internal. Out-of-band credentials reach git only as environment-level config, URL credentials are redacted from everything persisted or logged, Git LFS downloads are off and committed symlinks are written as plain files. `RepoTransport` lets tests replace git.

Part of [cognee-rs](https://github.com/topoteretes/cognee-rs) — see the [project README](../../README.md) for an architecture overview and how the pieces fit together.
