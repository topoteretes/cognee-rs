# cognee-cognify

Knowledge-graph extraction pipeline (classify → chunk → extract → summarize → index).

## Routes

Every item is routed by its `system_metadata.source` (`routing`, Python's
`cognify_route_for`). A code project's repo item (`code_repo`) runs the
deterministic code graph (`cognee-code-graph`) as the run's first task
(`tasks::run_code_routes`), with no LLM and no embedding; the rest run the
standard stages. All items share one run and its completion markers. A repo
item that fails to load is a per-item failure, as in Python's per-item run:
it is recorded in the run's `FailureReport` (stage `CodeGraph`) and the
failure policy decides the rest. `FailFast` stops at it; `RunToEnd` goes on
with the other items; under `FailedItems` a repo item that loaded counts as a
survivor and keeps its graph and completion marker. A per-file code item
(`code`, a lone source file `code_loader` stored) loads its code graph on its
own enola run, staged under its original file name in a temporary directory
(`cognee_code_graph::extract_code_file_graph`, Python's `code_files.py`),
untagged, with the same per-item failure handling. A DLT source stamped in
`system_metadata` (`dlt_source`) is not supported yet and fails the whole run
before any work, as does a legacy `dlt` row.
`routing::routes_need_llm` tells callers whether a run's items need the graph
extractor at all.

One Rust task runs both code routes, where Python runs one task per route, so
the task (and its telemetry) is named after the route that ran
(`tasks::code_routes_task_name`): `extract_code_files_graph` when every
code-routed item of the run is a per-file code item, `extract_code_repo_graph`
when a repo item is among them (a mixed run included). `build_cognify_pipeline`
is built before the items are known and always names it
`extract_code_repo_graph`.

`run_code_graph_pipeline` builds code-repo items alone in a
`code_graph_pipeline` run (Python's `remember(content_type="code")` run): the
same CODE_REPO adapter, not incremental, and on success each item is stamped
complete under both `cognify_pipeline` and `code_graph_pipeline`.

A dataset holding several code repositories is one enola cluster
(`code_cluster`, Python's `cluster.py`): cognify's CODE_REPO route loads every
member from the run's first repo item (`load_dataset_cluster`), each under its
own row, with the edges between repositories; `remember(content_type="code")`
plans the refresh (`plan_dataset_refresh`) and rebuilds the dataset's other
repositories with the new ones (`refresh_dataset_code_graph`), past
`CLUSTER_INLINE_REBUILD_LIMIT` only marking the rest for the next cognify
(`mark_code_repos_for_rebuild`).

## Global context index

`global_context_index` builds the retrieval-ready summaries above a dataset that
`improve(build_global_context_index=true)` writes: `GlobalContextSummary` buckets
and a root, embedded in `GlobalContextSummary_text`. The default
`GlobalContextIndexMethod::FromEntities` makes no LLM call (one bucket per document,
by tf·idf over the dataset's chunks, written only when its text changed);
`GlobalContextIndexMethod::Llm` summarizes vector-placed buckets of `TextSummary`
nodes with Python's prompts. Both are ports of Python's
`cognee/tasks/memify/global_context_index/`; the `from_entities` text is checked
against a fixture generated by Python's own functions
(`tests/fixtures/global_context_index/`).

## Pluggable graph extraction

By default the extraction stage calls an LLM once per chunk through `FactExtractor`.
`graph_backend::ChunkGraphExtractor` is the extension point that replaces that call
with something else — a local NER/relation model, an on-device runtime, a rule engine —
so the pipeline can run offline, on-premise or cheaply at volume:

```rust,ignore
let config = CognifyConfig::default().with_graph_backend(Arc::new(my_backend));
```

A backend returns exactly one result per `ChunkRef`, in input order, and may also take
over chunk summarization by reporting `summarizes_chunks() == true`:

```rust,ignore
async fn extract_graphs(
    &self,
    chunks: &[ChunkRef<'_>],
    ctx: &ExtractionContext<'_>,
) -> Result<Vec<ChunkGraphResult>, GraphBackendError>;
// ChunkGraphResult = Result<KnowledgeGraph, ChunkExtractionError>
```

Failure has two granularities, and the inner one is the one to reach for. A
`ChunkExtractionError` in a chunk's own slot fails **that chunk only** — its siblings in
the same batch still land in the graph, exactly as the LLM path loses one chunk to one
failed call. The outer `GraphBackendError` fails the **whole batch** and is for
model-won't-load / runtime-missing situations; since `chunks_per_batch` defaults to 2000,
a realistic run is one batch, so using it for a single bad chunk fails the entire run.
A failed chunk still occupies its slot: dropping it is an `ArityMismatch`, not a failure
report.

Everything after extraction — the abort-time partition, per-chunk failure accounting,
DB-aware edge dedup, node/edge expansion, ownership rows and the graph writes — is
backend-neutral and shared with the LLM path.

The only implementor in this repository is `MockChunkGraphExtractor`, which
`tests/graph_backend_seam.rs` drives the whole stage through. That is deliberate: real
implementations are expected to live in other crates. See the `graph_backend` module
docs before concluding the seam is dead code.
