# P1-02 — Vector retrieve-by-id

**Status:** completed

## Goal

Add a batched, order-agnostic "fetch by ID" primitive to the vector-database
abstraction: `VectorDB::retrieve(data_type, field_name, ids) -> Vec<SearchResult>`.
This is plumbing, not a retriever: it lets callers pull back the stored
`metadata` payload (and a zero placeholder score) for a known set of point
IDs without re-running a similarity search. It is a direct port of Python's
`VectorDBInterface.retrieve`. Phase 1's hybrid chunk lane needs it to expand
a `TextSummary` hit back to its source `DocumentChunk` (the "summary →
source-chunk backfill"); Phase 2's `load_centroids` will need it to hydrate
saved centroid vectors by ID. Landing it now, as its own trait method with
all four adapters kept in lock-step, avoids a follow-on trait-object churn
once the hybrid chunk lane starts consuming it.

## Prerequisites

- None from this plan. This is foundational, self-contained plumbing confined
  to `crates/vector`; it does not depend on any other phase-1 hybrid-retriever
  task landing first. Conversely, later tasks (the hybrid chunk lane's
  summary→chunk backfill, Phase-2 `load_centroids`) depend on **this** task.
- Assumed state: the `VectorDB` trait and its four implementors
  (`LanceDbAdapter`, `PgVectorAdapter`, `BruteForceVectorDB`, `MockVectorDB`)
  as they stand at commit `82310dc` (current `main` tip) — i.e. `search_similar`,
  `delete_points`, `collection_size` etc. already exist and follow the
  `CollectionNotFound`-on-missing-collection convention described below.

## Implementation steps

1. **Trait method.** In `crates/vector/src/vector_db_trait.rs`, add to the
   `#[async_trait] pub trait VectorDB: Send + Sync` block:
   ```rust
   async fn retrieve(
       &self,
       data_type: &str,
       field_name: &str,
       ids: &[Uuid],
   ) -> VectorDBResult<Vec<SearchResult>>;
   ```
   Make it a required method (no default body) — all four adapters get an
   explicit, reviewed implementation rather than inheriting a silently-wrong
   default. Doc-comment it with: empty `ids` → `Ok(vec![])` without touching
   storage; unknown collection → `Ok(vec![])` (not `CollectionNotFound`) —
   this is a deliberate divergence from `search_similar`/`delete_points`/
   `collection_size`, faithful to Python (see Parity notes); IDs not present
   in the collection are silently absent from the result, no error and no
   placeholder entry; result order is **not** guaranteed to match input-`ids`
   order (callers needing input order must re-sort/index by `SearchResult.id`
   themselves).

2. **`BruteForceVectorDB`** (`brute_force_vector_db.rs`): mirror
   `search_similar`'s read-lock-then-build pattern (line 151-197). Under
   `self.collections.read().await`, look up `Self::key(data_type, field_name)`;
   if absent, return `Ok(vec![])` (do **not** reuse the
   `.ok_or_else(CollectionNotFound)` idiom used elsewhere in this file — that
   is the intentional divergence for this method only). If present, filter
   `coll.points` for `ids.contains(&p.id)` and map each match to
   `SearchResult { id: p.id, score: 0.0, metadata: p.metadata.clone() }`. An
   empty `ids` slice should short-circuit to `Ok(vec![])` before taking the
   lock (mirrors `index_points`'s empty-input guard at line 116-118).

3. **`MockVectorDB`** (`mock_vector_db.rs`): identical shape to step 2 but
   over `self.collections.lock().unwrap()` (sync `Mutex`, `// lock poison is
   unrecoverable`) and `CollectionData::points` (line 37-40). Same missing-id
   and missing-collection behavior. Do not add call-logging (the
   `index_points_calls`/`create_collection_calls` logs exist to support
   assertions on those specific methods; `retrieve` has no equivalent
   consumer yet — skip it unless a Phase-1 chunk-lane test later needs it).

4. **`LanceDbAdapter`** (`lancedb_adapter.rs`): add `retrieve` inside the
   `impl VectorDB for LanceDbAdapter` block (after `search_similar`, line
   377-407, is a natural spot). Steps inside:
   - `if ids.is_empty() { return Ok(vec![]); }` — avoids building an
     `id IN ()` predicate, which mirrors the Python LanceDB adapter's
     explicit guard (`LanceDBAdapter.py:975-978`, "lance rejects as a parse
     error").
   - Build `name = collection_name(data_type, field_name)`; attempt
     `self.connection.open_table(&name).execute().await`; on
     `lancedb::Error::TableNotFound`, return `Ok(vec![])` (not
     `CollectionNotFound`) — matches `search_similar`'s error-mapping style
     (line 390-395) but with a different terminal outcome for this method.
   - Build the same hex-literal `id IN (X'..', X'..', ...)` predicate used by
     `index_points` (line 317-326) and `delete_points` (line 442-449) — reuse
     that byte-to-hex mapping rather than re-deriving it inline; factor a
     tiny shared helper (`fn id_in_predicate(ids: &[Uuid]) -> String`) if it
     keeps the three call sites in sync, or inline it identically — either is
     acceptable, but do not let the three predicates drift.
   - Run `table.query().only_if(predicate).execute().await`, collect
     `RecordBatch`es via `try_collect`, and pass them to the existing
     `id_metadata_from_batches` helper (line 122-150) — it already returns
     `HashMap<Uuid, HashMap<String, Value>>` keyed by id with no `_distance`
     column dependency (unlike `search_results_from_batches`, which requires
     `nearest_to` to have populated `_distance` — a plain `only_if` query has
     no such column, so `search_results_from_batches` must **not** be reused
     here).
   - Map the returned `HashMap` into `Vec<SearchResult>` with
     `score: 0.0` for every entry (the map naturally drops any requested id
     not found in storage — that is the missing-id behavior, for free).

5. **`PgVectorAdapter`** (`pgvector_adapter.rs`): add `retrieve` after
   `search_similar` (around line 463+). Steps:
   - `let coll = Self::collection_name(data_type, field_name)?;` (line 167,
     validates `[a-zA-Z0-9_]` before any SQL is built).
   - If `ids.is_empty()`, return `Ok(vec![])` immediately.
   - Do **not** call `has_collection` first as a gate — instead attempt the
     query and treat "relation does not exist" as `Ok(vec![])`, OR call
     `has_collection` up front and short-circuit to `Ok(vec![])` if `false`
     (either is acceptable; the existing `fetch_metadata` helper assumes the
     table exists and does not itself guard this, so prefer the explicit
     `has_collection` pre-check for clarity and to avoid parsing Postgres
     error codes).
   - For chunks of `ids` sized `BATCH_SIZE` (line 27, currently `100` — reuse
     this existing constant rather than introducing Python's `QUERY_BATCH_SIZE
     = 1000`; see Parity notes for why the mismatch is acceptable), run
     `SELECT id, metadata FROM "{coll}" WHERE id IN ($1::uuid, $2::uuid, ...)`
     — the same placeholder-building shape as `fetch_metadata` (line 206-210),
     parameterized (never string-interpolated UUIDs) to avoid injection.
   - Decode each row into `SearchResult { id, score: 0.0, metadata }` — reuse
     the object/else-empty-map decode already written in
     `row_to_search_result` (line 238-259) for the metadata half, but note
     that helper also reads a `"score"` column that this query does not
     select; either extend it with an optional-score variant or write a
     small `row_to_retrieve_result` sibling that always sets `score: 0.0` —
     do not add a fake `0 AS score` column to the SQL just to reuse the
     existing decoder verbatim (simpler to keep two small decode functions
     than to bend the query).
   - Accumulate across batches into one `Vec<SearchResult>` and return.

6. **Object safety check.** `Arc<dyn VectorDB>` is used pervasively in
   `crates/search` (`crates/search/src/retrievers/summaries_retriever.rs`
   line 17 — the `vector_db: Arc<dyn VectorDB>` field — and siblings such as
   `completion_retriever.rs`, `chunks_retriever.rs`, `triplet_retriever.rs`,
   plus `orchestration/search_execution_builder.rs`). Confirm
   `retrieve`'s signature (`&self`, `&str`, `&str`, `&[Uuid]` — all by
   reference, no generics) keeps the trait object-safe; it does, following
   the exact shape of `search_similar` and `delete_points`.

7. Run `cargo check --all-targets` (workspace default; add `--features
   pgvector,testing` where the crate under test needs it — check
   `crates/vector/Cargo.toml` for the exact feature names) to catch the four
   adapters simultaneously — a missing impl on any one is a compile error
   once `retrieve` is a required trait method with no default body.

## Parity notes

- **Python reference:** `cognee/infrastructure/databases/vector/
  vector_db_interface.py:82` — `async def retrieve(self, collection_name:
  str, data_point_ids: list[str])`, abstract, no default body.
- **Missing collection → empty, not error.** All three Python adapters that
  implement `retrieve` explicitly special-case a missing collection to `[]`
  rather than raising:
  - `LanceDBAdapter.py:963-999` — `except CollectionNotFoundError: return []`.
  - `PGVectorAdapter.py:434-462` — same `except CollectionNotFoundError: return []`.
  - `TursoVectorAdapter.py:265-289` — `if not await self.has_collection(...): return []`.
  This is a deliberate, documented divergence from every other Rust `VectorDB`
  method (`search_similar`, `delete_points`, `collection_size` all return
  `Err(VectorDBError::CollectionNotFound(..))` on a missing collection). Do
  not "fix" `retrieve` to be consistent with its siblings — consistency with
  Python is the contract here, since callers (the chunk-lane backfill) treat
  "nothing found" and "collection absent" identically.
- **Missing individual IDs → silently absent, no error, no placeholder.**
  Python builds a `WHERE id IN (...)` filter and returns whatever rows exist;
  requested IDs with no matching row simply do not appear in the output list.
  Same in Rust: no `Err`, no `None` placeholder, no ordering guarantee tying
  output position back to the input `ids` slice.
- **Order is not guaranteed.** Python's `retrieve` never sorts; it returns
  rows in whatever order the backend's `IN` scan/dedup loop produces (LanceDB:
  batch/row-scan order; pgvector/Turso: dedup-by-`seen_ids` insertion order
  across `QUERY_BATCH_SIZE`-sized batches). The Rust port must not promise
  input-order preservation either — document this on the trait method so
  callers (chunk-lane backfill, Phase-2 `load_centroids`) key results by
  `SearchResult.id` rather than by position.
- **`score` is always `0`,** not a real similarity score — Python's
  `ScoredResult(id=..., payload=..., score=0)` in every adapter (e.g.
  `PGVectorAdapter.py:461`, `LanceDBAdapter.py:996`). Rust: `score: 0.0_f32`
  on every `SearchResult` returned by `retrieve`. This is intentional — the
  field only carries meaning for similarity search, not direct fetch — and
  must not be confused with "zero similarity."
- **Deduplication.** pgvector/Turso Python both explicit-dedup by `seen_ids`
  across batches (defense against the same id appearing in more than one
  `QUERY_BATCH_SIZE` chunk, which cannot happen with a partition of a
  deduplicated input, but the guard is cheap and present in both — a
  behavior carried over from a shared code lineage). The Rust
  `BruteForceVectorDB`/`MockVectorDB` in-memory point lists cannot contain
  duplicate IDs by construction (upsert-by-id semantics, see
  `index_points`), so no extra dedup step is needed there; `PgVectorAdapter`
  batches a caller-supplied `ids` slice that could itself contain duplicates
  (e.g. a caller that didn't `dedup()` first) — either dedup `ids` on entry
  or accept that a duplicate input id yields a duplicate output row (a
  single-row `SELECT ... IN (...)` cannot itself produce two rows for one
  physical id, so duplicate inputs only ever cost redundant work, never
  incorrect output). No action required beyond noting this; do not add a
  `seen_ids` set unless a test demonstrates it's needed.
- **Empty `ids` short-circuits before touching storage** in every adapter —
  matches the Python LanceDB comment at `LanceDBAdapter.py:975-978` ("Avoid
  building an `id IN ()` filter, which lance rejects as a parse error;
  pgvector/chromadb return `[]` here too").
- **Batch size divergence (accepted, non-parity-breaking):** Python's
  `QUERY_BATCH_SIZE = 1000` (pgvector/Turso) chunks the `IN` list for
  parameter-count safety; the Rust `PgVectorAdapter` already has a
  `BATCH_SIZE = 100` constant used by `index_points`'s insert chunking. Reuse
  `BATCH_SIZE` for `retrieve`'s read-side chunking rather than introducing a
  second constant — this is a performance-only difference (more round trips
  for very large ID lists), not a structural/behavioral one, and the
  acceptance bar for this task is structural parity, not throughput parity.
- **UUID vs `str` ids.** Python's interface types `data_point_ids` as
  `list[str]`; Rust's is `&[Uuid]` (this workspace's convention throughout
  `vector_db_trait.rs` — `delete_points` already takes `&[Uuid]`). No
  behavior change, just noting the type already diverges from Python at the
  API boundary in the same way every other ID-taking method here does.
- **`importance_weight`** (locked decision #3, `DataPoint.importance_weight`)
  is not touched by this task — it lives in the `metadata` payload blob that
  `retrieve` already returns untouched (whatever `index_points` wrote is
  handed back verbatim); no separate plumbing is needed in `retrieve` itself.

## Risks & open items

- **Trait-object churn for out-of-tree adapters.** `retrieve` is added as a
  required method with no default body, so any `VectorDB` implementor outside
  this workspace (the brief's own docs mention a closed
  `cognee-vector-qdrant` crate in a code comment) will fail to compile until
  it adds an impl. If such a crate exists and is not in this repo, flag it
  to whoever owns it — this task cannot fix code it cannot see.
- **`has_collection` vs. catch-the-storage-error for pgvector's missing-collection
  check.** The two approaches (pre-check vs. catching a Postgres "relation
  does not exist" error) are both valid; this doc recommends the pre-check
  for readability, but if a reviewer prefers matching the Python
  try/except-on-error shape more literally, that is a fine, non-blocking
  alternative — note the choice in the PR description either way.
- **Shared `id IN (...)` predicate-building helper for LanceDB** (step 4) is
  a nice-to-have de-duplication across `index_points`/`delete_points`/
  `retrieve`; if it turns into a larger refactor than this task's scope
  warrants, inlining the third copy is acceptable and should not block this
  task — file a follow-up instead of scope-creeping P1-02.
- **No wire/CLI/HTTP exposure in this task.** `retrieve` is an internal
  trait method consumed by Rust callers (chunk-lane backfill, Phase-2
  `load_centroids`) — it is not itself one of the "hybrid knobs" that locked
  decision #8 requires exposing on the wire. Confirm no binding surface
  (`capi/`, `python/`, `ts/`, `java/`) needs a corresponding update; if a
  future task exposes vector retrieval directly over a binding, it should
  reference this trait method rather than re-deriving the semantics.
- **Existing datasets / no backfill** (locked decision #7) does not apply
  here — `retrieve` reads existing storage as-is; it introduces no new
  on-disk schema or migration.
