# P1-04 — importance_weight on DataPoint

**Status:** completed

## Goal

Add a Python-faithful `importance_weight: Option<f64>` field (default `Some(0.5)`) to the
base `DataPoint` model and propagate it along the `classify_documents` → `chunk` →
`summarize_text` chain, exactly as the Python reference does. This is a prerequisite for the
HybridRetriever's BM25 lane (P1-0x) and Phase 2 truth-weighting (deferred), both of which read
`importance_weight` off graph nodes / vector payloads to bias ranking. Because `Data.importance_weight`
already exists end-to-end in the ingestion/relational layer, this task is pure propagation — no new
migration, no new API surface.

## Prerequisites

- None within the hybrid-retriever plan — this is a foundational/base-model task other Phase 1
  tasks (BM25 lane, `get_neighborhood`, wire-level knobs) build on top of.
- Assumed state: `crates/models/src/data.rs` already has `Data.importance_weight: Option<f64>`
  (confirmed present), `crates/database/src/entities/data.rs` already has the matching column,
  and `m20260914_000001_baseline.rs` already creates the `importance_weight` column on the `data`
  table (all confirmed below) — i.e. the relational/ingestion side of this field was already
  ported in an earlier change. This task only touches the **graph-node / DataPoint** side.

## Implementation steps

1. **`DataPoint` field.** In `crates/models/src/data_point.rs`, add a private
   `fn default_importance_weight() -> Option<f64> { Some(0.5) }` helper next to the existing
   `default_feedback_weight()` (line 11-14). Add the new field directly after `feedback_weight`
   (line 89):
   ```rust
   #[serde(default = "default_importance_weight")]
   pub importance_weight: Option<f64>,
   ```
   Use `#[serde(default = "...")]` (not bare `#[serde(default)]`) so that deserializing an
   **old, pre-existing** graph node/vector payload that lacks the key yields `Some(0.5)` — the
   neutral rank called for by Decision 7 — rather than `None`/`null`. This mirrors Python's
   `importance_weight: float | None = 0.5` (`DataPoint.py:75`), which is also `Some`-by-default
   despite being `Optional`-typed.
2. **Constructors.** In `DataPoint::new` (~line 99-117) and `DataPoint::with_metadata`
   (~line 120-143), initialize `importance_weight: Some(0.5)` alongside the existing
   `feedback_weight: 0.5` line, so both paths start at the Python default.
3. **`classify_documents` glue.** In `crates/models/src/document.rs::classify_documents`
   (~line 115-181), immediately after `let mut base = DataPoint::new(class_name, None);`
   (line 127), set:
   ```rust
   base.importance_weight = Some(data.importance_weight.unwrap_or(0.5));
   ```
   This is the direct port of Python `classify_documents.py:144-146`:
   ```python
   importance_weight=data_item.importance_weight
       if data_item.importance_weight is not None
       else 0.5,
   ```
   Do this unconditionally for every document type (`TextDocument`, `PdfDocument`,
   `DltRowDocument`, etc.) — Python applies it identically across all `Document` subclasses via
   the shared constructor call.
4. **Chunk propagation (DLT branch).** In `crates/cognify/src/tasks.rs::extract_chunks_from_documents`,
   in the `document.document_type == "dlt_row"` short-circuit (~line 200-225), after building the
   single `DocumentChunk` (`DocumentChunk::new(...)`) and before pushing it to `all_chunks`, add:
   ```rust
   chunk.base.importance_weight = document.base.importance_weight;
   ```
   Do this unconditionally (unlike the existing `if document.base.belongs_to_set.is_some()` guard
   used for `belongs_to_set` at line 218) — `importance_weight` is always `Some` after step 3, so
   there is no "absent" case to skip.
5. **Chunk propagation (regular branch).** In the same function's non-DLT path, the existing loop
   at ~line 270-276:
   ```rust
   if document.base.belongs_to_set.is_some() {
       for chunk in &mut chunks {
           chunk.base.belongs_to_set = document.base.belongs_to_set.clone();
       }
   }
   ```
   covers `chunk_text`, `chunk_by_row`, and the `LoaderOutput::SingleChunk` case (all three
   funnel into the same `chunks: Vec<DocumentChunk>` before this loop runs). Add an adjacent,
   unconditional loop (or fold into the same loop body) that sets
   `chunk.base.importance_weight = document.base.importance_weight;` for every chunk. This is the
   Rust equivalent of Python's `TextChunker.read()` passing `importance_weight=self.document.importance_weight`
   at each of the three `DocumentChunk(...)` construction sites (`TextChunker.py:36`, `:58`, `:83`)
   — Rust's chunker (`crates/chunking/src/text_chunker.rs::chunk_text`) only receives a bare
   `document_id: Uuid`, not the full `Document`/`DataPoint`, so the propagation must happen at the
   call site in `tasks.rs` where both `document` and `chunks` are in scope, not inside the chunker
   itself.
6. **Summary propagation.** In `crates/cognify/src/summarization/extractor.rs::summarize_chunks`
   (~line 160-206), extend the pre-extracted owned-input tuple (currently
   `(usize, String, Uuid)` at line 176-180) to a 4-tuple that also carries
   `chunk.base.importance_weight: Option<f64>`. After
   `TextSummary::from_summarized_content(chunk_id, summarized, model_name)` constructs the summary
   (line 199-200), set:
   ```rust
   summary.base.importance_weight = importance_weight;
   ```
   before packing `(index, summary)` for the `try_collect`. This is the direct port of Python
   `summarize_text.py:81`: `importance_weight=chunk.importance_weight,` inside the `TextSummary(...)`
   constructor call (`summarize_text.py:73-82`).
7. **No new constructor params.** Do **not** add `importance_weight` as a parameter to
   `DocumentChunk::new` or `TextSummary::new`/`from_summarized_content`. Both already have several
   positional parameters and multiple call sites (including test call sites); overriding the field
   post-construction (steps 4-6) matches the established `belongs_to_set` idiom in this codebase
   and avoids a signature churn that would ripple through unrelated tests.
8. **Vector payload — no code change, verify only.** Confirm (do not modify) that
   `DocumentChunk::vector_metadata()` / `DataPoint::vector_metadata()` (used by the chunk
   `VectorPoint` construction in `tasks.rs` ~line 2731-2739, and analogously for entity/summary
   payloads elsewhere in the same function) serializes the whole `DataPoint` via
   `serde_json::to_value(self)`. Since the new field has no `skip_serializing_if`, it will always
   appear in the JSON map (as `"importance_weight": 0.5` or similar) once populated — this is
   intentional (Python's `model_dump()` includes it unconditionally too, being non-`None` by
   default).
9. **Compile and check.** Run `cargo check --all-targets`, then targeted tests for
   `cognee-models`, `cognee-cognify` (see Testing below), then `scripts/check_all.sh` for the
   final full-suite pass (fmt, clippy, capi/python/ts/java binding checks).

## Parity notes

- **Default value:** `Some(0.5)`, matching Python `DataPoint.importance_weight: float | None = 0.5`
  (`cognee/infrastructure/engine/models/DataPoint.py:75`). Despite the `Optional` type in both
  languages, the *default* is never `None` — `None`/absent only occurs transiently on the
  ingestion-time `Data.importance_weight` before the classify step normalizes it.
- **Null-coalescing at classify time:** Python `classify_documents.py:144-146` coalesces
  `data_item.importance_weight` to `0.5` when `None`. Rust step 3 (`document.rs`) does the same via
  `.unwrap_or(0.5)` — this is the single normalization point; every downstream consumer
  (chunk, summary) can assume `Some` is always populated after classification.
- **Propagation is a straight copy, no re-weighting:** at every hop (document → chunk → summary)
  the value is copied verbatim, never recomputed or blended. This matches Python exactly — none of
  `TextChunker.py:36/58/83` or `summarize_text.py:81` apply any transformation, just pass-through.
- **Old rows / existing datasets (Decision 7):** rows created before this change (whether stored
  as graph nodes or vector payloads) deserialize via `#[serde(default = "default_importance_weight")]`
  to `Some(0.5)` — the same neutral value as new rows whose source `Data.importance_weight` was
  `None`. No backfill migration is planned or needed; this is documented degradation, not a bug.
- **`f64` vs Python `float`:** both are IEEE-754 double precision; no representational divergence.
- **Serialization key name:** field serializes as `"importance_weight"` (no `#[serde(rename)]`),
  matching Python's pydantic field name exactly — required for cross-SDK JSON/graph-node parity.
- **`skip_serializing_if` intentionally omitted:** unlike `source_pipeline`/`source_task`/etc.
  (which use `skip_serializing_if = "Option::is_none"` because they are frequently absent),
  `importance_weight` is expected to be a real number essentially always, so it is emitted
  unconditionally — matching Python's non-optional-in-practice default.
- **DLT chunks are not exempt:** Python does not special-case `importance_weight` propagation for
  `DltRowDocument`/`DltRowDocument`-derived chunks (only *summarization* skips DLT chunks,
  `summarize_text.py:52-62`) — so step 4 propagates `importance_weight` on the DLT short-circuit
  path exactly like the regular path, unlike `belongs_to_set` which is conditionally propagated.
- **Scope boundary:** this task does **not** implement any BM25/HybridRetriever consumption of
  `importance_weight` — it only makes the value reliably present on every `DataPoint` so later
  Phase 1/2 tasks can read it off graph nodes and vector payloads.

## Risks & open items

- **Golden-fixture churn (flag for P1-11):** every graph node and vector payload JSON shape now
  includes `importance_weight`, which will break any e2e-cross-sdk byte-for-byte fixture
  comparisons (e.g. `test_add_parity.py`, `test_provenance_parity.py`) that do full-object
  equality rather than field-subset checks. This task does not update those fixtures; a follow-up
  task must regenerate/adjust them. Since the acceptance bar for the overall HybridRetriever effort
  is structural parity (not bit-identical), this is expected to require tolerance/allowlist
  adjustments rather than exact-match fixes.
- **`chunk_text`/`chunk_by_paragraph` API surface unchanged:** the chunker functions in
  `crates/chunking/` remain unaware of `importance_weight` (they only ever received a bare
  `document_id`); all propagation happens at the `tasks.rs` call site. If a future refactor moves
  chunk construction into the chunker crate itself, the propagation logic in steps 4-5 must move
  with it.
- **`Document.data_point_mut()` / `HasDataPoint` traversal:** `Document`, `DocumentChunk`, and
  `TextSummary` all implement `HasDataPoint` with default (no-op) `for_each_child_mut` — this task
  does not add any generic recursive-traversal propagation mechanism; propagation is done via
  explicit field copies at three specific call sites. If a future task introduces a generic
  "inherit parent DataPoint fields" traversal, `importance_weight` should be folded into it, but
  that is out of scope here.
- **`importance_weight` on `Entity`/`EntityType`/`EdgeType`:** Python's LLM-extracted entities do
  not receive `importance_weight` propagation from their source chunk in the reference
  implementation (only Document → DocumentChunk → TextSummary is wired) — Rust matches this by
  leaving entities at the class default (`Some(0.5)`) with no additional propagation. Verify this
  assumption holds if a future BM25/hybrid task expects entity-level importance weighting.
- **Feature not yet consumed:** this task purely plumbs the value through; nothing in the search/
  retrieval path reads `importance_weight` yet. The BM25 lane and Phase 2
  `use_truth_weight`/`build_truth_subspace` knobs (deferred, default-off) are the first consumers,
  specified in separate task docs.
