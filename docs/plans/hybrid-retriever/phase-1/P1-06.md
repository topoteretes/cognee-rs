# P1-06 — `get_neighborhood` on `GraphDBTrait`

**Status:** completed

## Goal

Add a batched `get_neighborhood(node_ids, depth) -> (nodes, edges)` method to
`GraphDBTrait` that returns the raw k-hop subgraph around a set of seed node
ids, in the same `(Vec<GraphNode>, Vec<EdgeData>)` shape as `get_graph_data`.
This is the Rust port of Python's `get_neighborhood`
(`cognee/infrastructure/databases/graph/graph_db_interface.py:599`) and is the
single graph-read primitive the hybrid entity lane (`hybrid/entities.py:30`,
a later task) needs to build per-entity edge bullets. Landing it here also
**fixes a real bug**: Ladybug's existing `get_connections`/`get_edges` always
report the *queried* node as the edge source regardless of which way the edge
is actually stored, so any future direction-sensitive consumer (this one
included) would silently see flipped edges — `get_neighborhood`'s ladybug
override must return the true stored `(source_id, target_id)` direction.

## Implementation steps

1. **Trait method + default impl** — in `crates/graph/src/traits.rs`, add
   after `get_connections` (line 177), before `get_graph_data` (line 179):
   ```rust
   async fn get_neighborhood(
       &self,
       node_ids: &[String],
       depth: usize,
   ) -> GraphDBResult<(Vec<GraphNode>, Vec<EdgeData>)> { .. }
   ```
   Give it a default body so no existing implementor needs to change in the
   same commit that adds the trait method. **Complete implementor census (8
   total, verified against the current tree):** the three *real* backends
   —`LadybugAdapter` (`ladybug.rs:587`), `MockGraphDB` (`mock.rs:74`,
   `testing`-feature-gated), `PgGraphAdapter` (`pg_graph_adapter.rs:343`)—
   override it per steps 2-4; the *five test doubles*—four `TestGraphDb`
   copies (`search/src/orchestration/search_execution_builder.rs:408`,
   `search/src/retrievers/cypher_nl_retrievers.rs:391`,
   `search/src/retrievers/graph_completion_retriever.rs:393`,
   `search/src/retrievers/temporal_retriever.rs:698`) plus http-server's
   `FailingGraphDB` (`http-server/src/health.rs:746`)—inherit the default body
   and need **no** change. This is deliberately unlike P1-02 (which added a
   *required* method and had to stub every implementor): the default body here
   makes the trait addition non-breaking for all five test doubles and any
   out-of-tree implementor, so this task touches only the three real backends.
   Default algorithm: BFS
   layered over `Self::get_connections` (already in scope, no new import
   needed — `HashMap`/`HashSet` are already imported at traits.rs:9):
   - Early-return `Ok((vec![], vec![]))` if `node_ids.is_empty()`.
   - Seed `visited: HashSet<String>` and `frontier: Vec<String>` from
     `node_ids`; seed a `nodes_by_id: HashMap<String, NodeData>` by calling
     `self.get_node(id)` for each seed (so isolated seeds with no edges still
     appear in the output, matching `get_neighborhood`'s "all nodes ... within
     depth hops of any seed" contract for the zero-edge case).
   - For each of `depth` layers: for every id in `frontier`, call
     `self.get_connections(id).await?`; for each
     `(source_node, edge_props, target_node)` triple, read `"id"` off
     `source_node`/`target_node` and `"relationship_name"` off `edge_props`
     to reconstruct an `EdgeData` tuple; dedup edges via a
     `HashSet<EdgeKey>` (the existing `(String, String, String)` alias at
     traits.rs:15) keyed on `(source_id, target_id, relationship_name)`;
     insert both endpoint nodes into `nodes_by_id`; whichever endpoint is not
     `id` is a candidate neighbor — add it to the next frontier only if not
     already in `visited`.
   - Stop early if a layer produces an empty next-frontier.
   - Return `(nodes_by_id.into_iter().collect(), edges)`.
   - **Known simplification, documented not fixed here**: at `depth == 0` the
     loop body never runs, so this default path returns only the seed nodes
     with **no** edges — even edges directly between two seeds are omitted.
     The two real-backend overrides (steps 2-3) do not have this gap (see
     Parity notes). Phase 1 only ever calls with `depth == 1`, so this is not
     a blocking concern; flag it in "Risks" rather than special-casing the
     default impl.
   - Also add a one-line bullet for `get_neighborhood()` to the trait's
     top-of-file "## Graph Queries" doc-comment list (traits.rs:46-52).

2. **Ladybug override (fixes the direction bug)** — in
   `crates/graph/src/ladybug.rs`, add an override inside
   `impl GraphDBTrait for LadybugAdapter` (place it near `get_connections`,
   lines 1001-1085, or `get_nodeset_subgraph`, line 1299 — either location is
   fine, this file already groups graph-query methods loosely). Reuse the
   exact patterns already proven correct elsewhere in this file:
   - Escape and join `node_ids` into a bracketed, quoted Cypher list
     (`id_list`), same escaping helper (`.replace('\\', "\\\\").replace('\'',
     "\\'")`) used throughout this file (e.g. line 971).
   - Neighbor discovery (undirected is correct here — direction only matters
     for the edges we return, not for which node ids count as "within depth
     hops"): issue
     `MATCH (seed:Node)-[r:EDGE*1..{depth}]-(neighbor:Node) WHERE seed.id IN [{id_list}] RETURN DISTINCT neighbor.id`,
     mirroring the Python ladybug adapter's own variable-length-path query
     (`ladybug/adapter.py:2723-2724`, `MATCH (seed:Node)-[r*1..{depth}]-(neighbor:Node)`),
     adapted to this Rust adapter's convention of always naming the
     relationship type (`:EDGE`) in the pattern.
   - Union `node_ids` with the discovered neighbor ids into `all_ids`
     (`HashSet<String>`), rebuild a second `id_list` from it.
   - Fetch full node rows for `all_ids` using the exact node-by-id-list query
     and parse loop already used at `get_nodeset_subgraph`
     (ladybug.rs:1386-1414, `MATCH (n:Node) WHERE n.id IN [...] RETURN n.id AS id, n.name AS name, n.type AS type, n.properties AS properties`,
     via `self.parse_node_data`).
   - Fetch edges with the **directed** query already used at
     `get_filtered_graph_data` (ladybug.rs:1274-1275) and `get_nodeset_subgraph`
     (ladybug.rs:1417-1418):
     `MATCH (a:Node)-[r:EDGE]->(b:Node) WHERE a.id IN [{id_list}] AND b.id IN [{id_list}] RETURN a.id, b.id, r.relationship_name, r.properties`.
     This is the fix: `a.id`/`b.id` come straight from the directed pattern
     match, never reassigned to "whichever side is the queried node" the way
     `get_connections`'s undirected pattern does.
   - Parse edge rows with the same `Self::EDGE_QUERY_COLUMN_COUNT` (=4,
     ladybug.rs:154) / `sanitize_json_control_chars` pattern used at
     ladybug.rs:1281-1294.
   - This mirrors Python's own `get_neighborhood` structure exactly:
     traversal query for reachable ids (ladybug/adapter.py:2723-2732) then a
     separate **directed** edges query over the collected id set
     (ladybug/adapter.py:2768-2773, `MATCH (n:Node)-[r]->(m:Node) WHERE n.id IN $ids AND m.id IN $ids`).

3. **Postgres override** — in `crates/graph/src/pg_graph_adapter.rs`, add an
   override inside `impl GraphDBTrait for PgGraphAdapter` (near
   `get_id_filtered_graph_data`, lines 1207-1267, which is the closest
   existing template for an id-set node+edge fetch, minus the recursion).
   Port the Python Postgres adapter's single-query design
   (`postgres/adapter.py:948-1017`) as raw SQL via
   `Statement::from_sql_and_values`:
   - One query, positional binds `$1` = `node_ids: Vec<String>` (bound as
     `sea_orm::Value` the same way `has_edges` binds its `Vec<String>` arrays,
     pg_graph_adapter.rs:592-608, `sources.into()`), `$2` = `depth as i64`.
   - `WITH RECURSIVE neighborhood(id, hops) AS (SELECT unnest($1::text[]), 0
     UNION SELECT CASE WHEN e.source_id = n.id THEN e.target_id ELSE
     e.source_id END, n.hops + 1 FROM neighborhood n JOIN graph_edge e ON
     (e.source_id = n.id OR e.target_id = n.id) WHERE n.hops < $2), ids AS
     (SELECT DISTINCT id FROM neighborhood)` — identical shape to
     `postgres/adapter.py:965-975`, table/column names match this crate's
     `GNode`/`GEdge` `Iden` impls (pg_graph_adapter.rs:44-109:
     `graph_node`/`graph_edge`, `source_id`/`target_id`).
   - `UNION ALL` two result halves discriminated by a literal `kind` column,
     same as Python: node half `SELECT 'node', gn.id, gn.name, gn.type,
     gn.properties, NULL, NULL, NULL, NULL FROM graph_node gn JOIN ids ON
     gn.id = ids.id`; edge half `SELECT 'edge', NULL, NULL, NULL, NULL,
     ge.source_id, ge.target_id, ge.relationship_name, ge.properties FROM
     graph_edge ge WHERE ge.source_id IN (SELECT id FROM ids) AND
     ge.target_id IN (SELECT id FROM ids)` — note `ge.source_id`/`ge.target_id`
     are selected straight off the table with no CASE-swap, so direction is
     correct by construction (same as the existing `get_connections`
     override at pg_graph_adapter.rs:763-830, which already got this right).
   - Alias the edge half's properties column `AS edge_properties` (not
     `properties`) to avoid a name collision with the node half's
     `properties` column in the same result set — same reason Python does
     this (`postgres/adapter.py:990` uses `edge_properties` as the alias).
   - Parse rows by branching on the `kind` column: `"node"` rows go through
     `Self::parse_node_row` (pg_graph_adapter.rs:281-305, expects columns
     `id`/`name`/`type`/`properties` — all present and non-null only on node
     rows); `"edge"` rows go through
     `Self::parse_edge_row_cols(row, "source_id", "target_id",
     "relationship_name", "edge_properties")` (pg_graph_adapter.rs:319+,
     already supports custom column names for exactly this reason).
   - Empty `node_ids` short-circuits to `Ok((vec![], vec![]))` before issuing
     any query, matching `get_id_filtered_graph_data`'s existing guard
     (pg_graph_adapter.rs:1211-1213).

4. **Mock override** — in `crates/graph/src/mock.rs`, add an override inside
   `impl GraphDBTrait for MockGraphDB` that does **not** call
   `self.get_connections` (see Files-touched note on the relationship-name
   drop bug). Lock `self.nodes` and `self.edges` once, then:
   - Seed `visited`/`frontier` from `node_ids` (dedup via `HashSet<String>`);
     seed `nodes_by_id` by looking up every seed directly in the `nodes` map
     (so isolated seeds are still returned).
   - For `depth` layers, scan the full `edges: Vec<EdgeData>` once per layer
     (or precompute an adjacency index if preferred — the mock has no
     performance requirement, correctness is what matters) for edges where
     `src == id || tgt == id` for `id` in the current frontier; push the
     **unmodified** `(src, tgt, rel, props)` tuple into the output (dedup via
     `HashSet<EdgeKey>`), insert both endpoints' `NodeData` from `self.nodes`
     into `nodes_by_id`, and enqueue the not-`id` endpoint into the next
     frontier if unvisited.
   - Push `"get_neighborhood".to_string()` onto `self.call_log`, matching the
     existing logging convention on `get_graph_data` (mock.rs:270-273) and
     `get_nodeset_subgraph` (mock.rs:393-396) — later hybrid-retriever tests
     can assert call counts/arguments the same way.
   - Because Mock's `edges` tuples already store true `(source_id,
     target_id)` from `add_edge`/`add_edges` with no reassignment anywhere in
     this override, direction is correct by construction — same reasoning as
     the Postgres adapter.

## Parity notes

- **Signature simplification vs Python, intentional**: Python's abstract
  signature is `get_neighborhood(node_ids, depth=1, edge_types=None)`
  (`graph_db_interface.py:599-604`). This task omits `edge_types` — the only
  Phase 1 consumer (`hybrid/entities.py:30`, `await
  graph_engine.get_neighborhood(entity_ids, depth=1)`) never passes it. A
  future task may extend this method (or add a sibling) if edge-type-filtered
  traversal is needed; do not block this task on it.
- **`depth` type**: Python `int` (any depth incl. 0 or negative in theory);
  Rust `usize` (cannot go negative, `depth: 0` is the meaningful lower
  bound). No behavior change for the only value Phase 1 uses (`depth = 1`).
- **True stored edge direction is the whole point of this task** (locked
  decision 6). `get_connections`/`get_edges` in `ladybug.rs` are undirected
  Cypher patterns (`MATCH (n:Node)-[r:EDGE]-(m:Node)`, lines 940, 971, 1015)
  that always bind the *queried* node to `n` and therefore always report it
  as the edge source in their output tuples — regardless of which side of
  the edge it actually is. `get_neighborhood`'s ladybug override must not
  inherit this: its final edge query is directed (`-[r:EDGE]->`) over the
  resolved node-id set, exactly like the pre-existing (and already-correct)
  `get_filtered_graph_data`/`get_nodeset_subgraph` edge queries in the same
  file. This task does not change `get_connections`/`get_edges` themselves —
  only `get_neighborhood` is required to be direction-correct; fixing the
  other two methods, if ever needed, is separate scope.
- **Postgres and Mock were already direction-correct** in their existing
  `get_connections` (pg_graph_adapter.rs:763-830 joins `n.id = e.source_id`,
  `m.id = e.target_id` unconditionally; mock.rs:237-267 pushes the stored
  `(src, tgt)` pair unmodified). Their `get_neighborhood` overrides exist for
  **query-count efficiency** (one round trip vs. one `get_connections` call
  per frontier node per hop), not to fix a direction bug — don't mistake
  "override exists" as implying "was also buggy".
- **Consumer partitioning is out of scope here**: `get_neighborhood` returns
  the raw 1-hop subgraph — nodes reachable within `depth` hops plus **every**
  edge whose both endpoints are in that resolved set, including
  neighbor-to-neighbor edges that touch no seed. The consumer,
  `hybrid/entities.py:47-73` (`_partition_neighborhood`), filters this down to
  edges incident to a seed entity only, and explicitly drops neighbor-neighbor
  edges (a triple is attached to `connections[entity_id]` only when
  `entity_id` is one of its two endpoints — `entities.py:66-71`). Do not
  pre-filter inside `get_neighborhood`; its contract matches `get_graph_data`'s
  "give me the subgraph, caller partitions it" shape.
- **Existing datasets**: no schema/data change here — this is a pure
  read-path addition. No backfill needed (locked decision 7 is not
  triggered by this task).
- **`depth == 0` divergence between the default trait impl and the two real
  overrides**: see step 1's "known simplification" bullet. The ladybug and
  Postgres overrides both compute a final node-id set first and then query
  edges over that whole set, so seed-to-seed edges surface even at `depth =
  0`; the generic default (BFS-over-`get_connections`, unused in practice
  once all three backends override) does not run its loop body at all when
  `depth == 0` and so omits them. Not exercised by Phase 1 (`depth` is always
  `1`); documented so it isn't rediscovered as a surprise later.

## Risks & open items

- `depth == 0` behaves inconsistently between the default trait impl (no
  edges at all) and the ladybug/Postgres overrides (seed-to-seed edges
  included) — see Parity notes. Not exercised by Phase 1; reconcile if a
  later task ever calls with `depth != 1`.
- `get_connections`/`get_edges` in `ladybug.rs` remain undirected/buggy after
  this task — only `get_neighborhood` is fixed. Any *other* existing caller
  of `get_connections` that assumes direction (grep before relying on it
  elsewhere) is still exposed to the pre-existing bug; out of scope here.
- `MockGraphDB::get_connections` still silently drops `relationship_name`
  after this task (mock.rs:251, `let (src, tgt, _, props) = ...`) — this
  task's mock override avoids the bug by not calling `get_connections`, but
  the underlying gap in `get_connections` itself is not fixed. Worth a
  follow-up cleanup ticket since it could bite any other future consumer of
  `MockGraphDB::get_connections`.
- The `P1-10.md` prerequisite-list drift noted above (references
  "P1-06/P1-07/P1-08 (chunk ranking, pairs merge, entity/fact building)")
  should be corrected once whoever owns that doc reads this one — flagged
  here rather than edited directly, since editing another task's doc is out
  of this task's scope.
- Ladybug's variable-length-hop Cypher (`-[r:EDGE*1..{depth}]-`) is only
  verified against Phase 1's `depth = 1` case in this task's tests; larger
  depths are plausible given the Python precedent but untested here.
- Default/Mock `get_neighborhood` capture only edges incident to a queried frontier node, whereas Ladybug/PgGraph return every edge internal to the resolved id-set; this diverges at depth>=1 (neighbor-to-neighbor edges omitted by default/mock). Benign for Phase 1: the sole consumer keeps only seed-incident edges and depth is always 1.
