# P1-05 — Shared helpers + payload fixes

**Status:** completed

## Goal

Three small, independent shared-infrastructure changes that later HybridRetriever
tasks (BM25 lexical lane, facts/EdgeType lane, completion prompt wiring) all
depend on: (a) hoist the private edge-retrieval-text rule out of
`cognee-cognify` into a public `cognee-models` helper so any future lane can
recompute the exact text an `EdgeType`/`Triplet` vector id was derived from;
(b) give the Rust `TextSummary` a real `source_chunk_id` field and emit it in
the vector payload so the hybrid pairing algorithm (`pairs.py:49`) can join
summary hits back to their source chunk the same way Python does; (c) add the
default hybrid completion prompt template constant next to the existing
RAG/graph ones. None of this changes retrieval behavior yet — it only prepares
the ground.

## Implementation steps

### (a) Hoist `edge_retrieval_text` into `cognee-models`

1. Confirm the dependency direction first: `crates/cognify/Cargo.toml`
   depends on `cognee-models` (`cognee-models = { path = "../models", ... }`,
   Cargo.toml:24), not the other way around. `GraphEdgePair` is defined in
   `crates/cognify/src/graph_integration/types.rs:29` (fields:
   `source_entity_id`, `target_entity_id`, `relationship_name: String`,
   `properties: HashMap<String, String>`), which `cognee-models` cannot
   reference without a cyclic dependency. **The hoisted helper must therefore
   take primitive `&str` parameters, not `&GraphEdgePair`.**
2. In `crates/models/src/edge_type.rs`, add a new associated function next to
   `EdgeType::deterministic_id` (models/src/edge_type.rs:39-46):
   ```rust
   /// Resolve the retrieval text for an edge, mirroring Python's
   /// `get_edge_retrieval_text(edge_text, relationship_name)`
   /// (prepare_edges_for_storage.py via index_graph_edges.py:33-53):
   /// prefer the nonblank `edge_text`, fall back to the nonblank
   /// `relationship_name`, else return an empty string (caller drops empties).
   pub fn retrieval_text(edge_text: Option<&str>, relationship_name: &str) -> String {
       if let Some(text) = edge_text.map(str::trim).filter(|s| !s.is_empty()) {
           return text.to_string();
       }
       relationship_name.trim().to_string()
   }
   ```
   This is a byte-for-byte behavioral copy of the current private fn body in
   `crates/cognify/src/tasks.rs:1569-1582` (docstring at 1564-1568) — only the
   parameter shape changes (two `&str`-ish params instead of one
   `&GraphEdgePair`).
3. In `crates/cognify/src/tasks.rs`, replace the body of the private
   `edge_retrieval_text` fn (tasks.rs:1569-1582) with a one-line adapter:
   ```rust
   fn edge_retrieval_text(edge_pair: &GraphEdgePair) -> String {
       cognee_models::EdgeType::retrieval_text(
           edge_pair.properties.get("edge_text").map(String::as_str),
           &edge_pair.relationship_name,
       )
   }
   ```
   Keep the fn name and signature identical so the two existing call sites —
   tasks.rs:1026 (`edge_type_counts` construction, feeding
   `EdgeType::new_deterministic` at tasks.rs:1036) and tasks.rs:3000
   (`edge_text_by_triple` map, feeding the Triplet provenance copy) — need no
   changes. `cognee_models::EdgeType` is already imported via the `cognee_models::{...}`
   use block at tasks.rs:43-46; add `EdgeType` to that import list if it is
   not already present (verify: `EdgeType` is already used at tasks.rs:1019
   via `EdgeType::new_deterministic`, so the import should already cover it).
4. This is prep for the (not-yet-written) BM25/facts lane task: that task
   will call `cognee_models::EdgeType::retrieval_text` directly (with the
   `edge_text`/`relationship_name` it reads back off a stored `EdgeType`
   vector-point payload or a re-walked graph edge) to recompute the same
   `EdgeType`/`Triplet` vector id that `index_graph_edges` used at indexing
   time — do not reuse the `LexicalRetriever`'s process-lifetime `OnceCell`
   corpus cache for this (locked decision 5: BM25 rebuilds its corpus
   per-query).

### (b) `source_chunk_id` on `TextSummary`

5. In `crates/cognify/src/summarization/models.rs`, add a new field to the
   `TextSummary` struct (after `made_from`, models.rs:34-37):
   ```rust
   /// Source chunk id, duplicated as a flat field for vector-payload lookup
   /// (matches Python's `TextSummary.source_chunk_id: Optional[str]`,
   /// cognee/tasks/summarization/models.py:35). Always set equal to
   /// `made_from` at construction time — kept as a distinct field only
   /// because Python's hybrid pairing code keys off this exact payload
   /// name (`hybrid/pairs.py:49`), not off a generic "made_from"/"chunk_id" key.
   pub source_chunk_id: Option<Uuid>,
   ```
   Store it as `Option<Uuid>` (not `Option<String>`): Rust's `made_from` is
   already a bare `Uuid` (not a nested `DocumentChunk` like Python's), so
   keeping `source_chunk_id` typed avoids a redundant string/Uuid parse round
   trip; it serializes to the same JSON string shape as Python's `str(chunk.id)`.
6. In `TextSummary::new` (models.rs:59-75), set `source_chunk_id: Some(chunk_id)`
   alongside the existing `made_from: Some(chunk_id)` — same value, set once,
   at the same call site. No public signature change is needed (the
   `chunk_id: Uuid` parameter already exists); `from_summarized_content`
   (models.rs:80-95) delegates to `new` so it picks this up for free.
7. In `crates/cognify/src/tasks.rs`, in the `TextSummary` vector-point builder
   (~tasks.rs:2911-2938, inside the `.map(|(summary, vector)| ...)` closure;
   chunk_id write at :2927-2929), add a sibling write next to the existing
   `chunk_id` one:
   ```rust
   if let Some(made_from) = summary.made_from {
       point = point.with_metadata("chunk_id", json!(made_from.to_string()));
   }
   if let Some(source_chunk_id) = summary.source_chunk_id {
       point = point.with_metadata("source_chunk_id", json!(source_chunk_id.to_string()));
   }
   ```
   **Keep `chunk_id` as-is for back-compat** — per the task brief, do not
   remove or rename it; no current retriever reads either key on
   `TextSummary` payloads yet (`grep` over `crates/search/src` confirms
   `summaries_retriever.rs` does not reference `chunk_id`/`source_chunk_id`
   today), so this is purely additive.
8. Python sets `source_chunk_id=str(chunk.id)` unconditionally alongside
   `made_from=chunk` at construction (`summarize_text.py:74-81`) — there is no
   code path where the two diverge in Python either, so the Rust invariant
   (`source_chunk_id == made_from` always, from `TextSummary::new` onward) is
   faithful, not a divergence.

## Parity notes

- **Edge retrieval text rule** — exact port of
  `get_edge_retrieval_text(edge_text, relationship_name)`
  (`cognee/modules/graph/utils/prepare_edges_for_storage.py`, invoked from
  `cognee/tasks/storage/index_graph_edges.py:33-53`): nonblank `edge_text`
  wins; else nonblank `relationship_name`; else empty string (caller drops
  the edge from `EdgeType` vector-indexing). "Nonblank" = trimmed and
  non-empty in both languages. No behavior change from the pre-existing
  Rust private fn — only its location and signature move.
- **`EdgeType` id scheme is unaffected** — `EdgeType::deterministic_id`
  still does `uuid5(NAMESPACE_OID, "EdgeType:<relationship_name>")`
  (edge_type.rs:39-46); this task does not touch id derivation, only the
  *text* that later gets fed into it (already correct) and exposes the rule
  publicly so a per-query BM25/facts lane can recompute it without
  depending on `cognee-cognify`'s private fn or its `GraphEdgePair` type.
- **`source_chunk_id`** — Python: `TextSummary.source_chunk_id: Optional[str] = None`
  (`cognee/tasks/summarization/models.py:35`), set via `str(chunk.id)` at
  construction (`summarize_text.py:78`), consumed by
  `cognee/modules/retrieval/hybrid/pairs.py:49`
  (`display_value(summary_payload.get("source_chunk_id"))`) to join a
  `TextSummary_text` vector hit back to its source chunk. Rust: typed
  `Option<Uuid>`, same value as `made_from`, serialized as the same string
  shape in the vector payload (`Uuid::to_string()` == Python's `str(uuid)`).
  This task only adds the field and the payload emission — the pairing
  algorithm itself (`chunk_summary_pairs`) is out of scope, ported in the
  HybridRetriever task.
- **Existing datasets** — per locked decision 7, no backfill migration:
  `TextSummary` points indexed before this change lack `source_chunk_id` in
  their stored payload. Document this as expected degradation (pairing falls
  back to whatever the hybrid task's None-handling does, mirroring Python's
  own `if not chunk_id: logger.warning(...); continue` at pairs.py:50-54) —
  do not attempt to re-index old summaries.
- **Prompt template** — verbatim content parity with
  `hybrid_context_for_question.txt` (5 lines: question line, instruction
  line, blank line, "Context:" line, context line), modulo the
  Jinja2-`{{ }}` → Rust-`{ }` placeholder syntax difference that already
  exists for every other `DEFAULT_*_USER_PROMPT_TEMPLATE` in this file — not
  a new divergence, an established one.

## Risks & open items

- `source_chunk_id` is currently write-only: nothing in `crates/search`
  reads it yet. That's intentional (pairing logic is a later task), but it
  means this task's payload change is unverifiable end-to-end until the
  HybridRetriever task lands — testing here is limited to asserting the
  payload shape, not behavior.
- The brief's suggested prompt-template string (no backticks) was corrected
  against the actual Python prompt file during verification; if a later task
  re-derives this constant from the brief text instead of this doc, it will
  silently diverge from both Python and the existing Rust prompt-template
  style. Flag this doc as the source of truth for the exact string.
- `importance_weight` on `DataPoint`/`TextSummary` (locked decision 3) has
  now LANDED (P1-04): the field lives on the base `DataPoint`
  (`crates/models/src/data_point.rs:106-107`, default `Some(0.5)`) and is
  already emitted into the `TextSummary` payload via the whole-DataPoint dump
  (`summary.base.vector_metadata()`, tasks.rs:2918). Therefore this task adds
  **only** the `source_chunk_id` key as a sibling; do NOT add a parallel
  manual `importance_weight` emission (it would duplicate the dump). The
  adjacent code is shared, but there is nothing left to reconcile.
- Confirm during implementation whether any other crate (bindings, HTTP
  server DTOs) mirrors the `TextSummary` struct field-for-field (e.g. a
  serde-derived wire type in `crates/http`/`crates/*-bindings`) and needs the
  new `source_chunk_id` field added in parallel to avoid a silent schema gap.
