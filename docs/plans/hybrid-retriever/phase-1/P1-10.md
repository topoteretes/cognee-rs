## Goal

Extend `SearchOrchestrator::build_used_graph_element_ids` so that, when the
active search type is `HYBRID_COMPLETION`, the session-cache `used_graph_element_ids`
snapshot picks up chunk ids, entity ids, and entity-edge endpoint ids from the
hybrid retriever's context items — not just the `source_id`/`target_id`/`edge_id`
fields graph-traversal retrievers already populate. This is the Rust port of
Python's `extract_context_object_ids` (`hybrid/context.py:33-58`), which feeds
`used_graph_element_ids` into `generate_completion_with_session` so that
follow-up-turn tracing and memify feedback attribution work for hybrid answers.
The second half of this task ports a curated slice of the two Python hybrid
unit-test files into Rust so the ranking, pairs, entity-bullet, and fact-gating
logic added in P1-05..P1-09 has regression coverage before this repo carries a
hybrid retriever in production paths.

## Implementation steps

1. **Confirm the P1-09 payload shape.** Before touching the orchestrator, read
   whatever `crates/search/src/retrievers/hybrid_retriever.rs` (or equivalent,
   landed by P1-09) puts into `SearchItem.payload` for each context item kind:
   chunk items, entity items, fact items. This doc assumes (see Parity notes)
   that:
   - chunk items carry `"id"` (the `DocumentChunk` id, mirrors
     `result_id()` in `hybrid/results.py:21-23`),
   - entity items carry `"id"` (entity/graph-node id) and a nested
     `"edges": [ { "source_id": ..., "target_id": ..., ... } ]` array mirroring
     the bullet dicts built in `hybrid/entities.py:183-201`,
   - fact items carry `"id"` but must be **excluded** from node-id extraction
     (Python comment at `hybrid/context.py:34`: "Facts are intentionally
     excluded: their ids are EdgeType vector rows, not graph nodes").
   If P1-09 landed a different shape (e.g. a discriminant `"kind"` field), use
   that instead and note the divergence at the top of this file's "Parity
   notes" section when you edit it in-flight.

2. **Extend `build_used_graph_element_ids`** in
   `crates/search/src/orchestration/search_orchestrator.rs` (function starts
   at line 88 today). Keep the existing `source_id`/`target_id`/`edge_id`
   extraction (used by graph-traversal retrievers such as `NaturalLanguage`/
   `GraphCompletion`) untouched, and add, per item:
   - if `payload["id"]` is a string and the item is **not** a fact item (see
     discriminant note above), insert it into `node_ids`;
   - if `payload["edges"]` is a JSON array, iterate it and for each edge
     object insert `edge["source_id"]` and `edge["target_id"]` (both as
     strings) into `node_ids` — mirrors `hybrid/context.py:50-56`.
   - Do **not** add anything to `edge_ids` for hybrid items: Python's
     `extract_context_object_ids` never populates an `edge_ids` key at all
     (only `{"node_ids": [...]}` is ever returned) — this is a real behavioral
     divergence from the existing graph-traversal path in this same function,
     which does populate `edge_ids` from an explicit `edge_id` field. Preserve
     both behaviors side by side; do not unify them.
   - Keep dedup via the existing `HashSet<String>` and the existing sort
     before returning, so combined output (graph-traversal ids ∪ hybrid ids)
     stays deterministic.

3. **Decide the fact-exclusion discriminant.** The cleanest option compatible
   with the existing untagged `payload: Value` shape: hybrid fact items should
   simply **omit** an `"edges"` field and, per step 1, ideally omit `"id"` too
   or tag themselves so this function can skip them (e.g. a payload key like
   `"item_kind": "fact"` set by P1-09, or facts simply never carrying an
   `"id"` key that looks like a node id — confirm against P1-09's actual
   shape). Write the extractor so it degrolds safely either way: if P1-09
   used a `"kind"`/`"item_kind"` tag, gate on it; if it relies on facts
   omitting `"id"`, no extra gate is needed. Document whichever was actually
   used in the code comment above the function, matching the existing
   comment style at lines 84-87.

4. **Wire nothing else in the call site.** The call at line ~560
   (`let used_graph_element_ids = build_used_graph_element_ids(context.as_deref());`)
   inside `SearchOrchestrator::search` already runs for every search type
   whenever a session id + session manager + `SearchOutput::Text` answer are
   present, so `HYBRID_COMPLETION` gets this for free once the extractor
   handles hybrid payload shapes — no branching on `request.search_type` is
   needed in `search_orchestrator.rs` itself.

## Parity notes

- **Exact node-id sources** (Python `hybrid/context.py:33-58`,
  `extract_context_object_ids`):
  - `chunks[*]` → `result_id(chunk)` (`hybrid/results.py:21-23`: payload `"id"`
    first, else `.id` attribute) → `node_ids`.
  - `entities[*]["id"]` → `node_ids` (via `display_value`, so numeric/UUID/bool
    ids are stringified, empty/whitespace-only strings are dropped).
  - `entities[*]["edges"][*]["source_id"]` and `["target_id"]` → `node_ids`.
  - **`facts` are never read** — comment at line 34 is explicit that fact ids
    are `EdgeType` vector-row ids, not graph node ids, so mixing them into
    `node_ids` would be wrong for any downstream consumer that expects graph
    node ids (e.g. neighborhood re-hydration).
  - Result is `None` if the accumulated `node_ids` set is empty (Python:
    `{"node_ids": sorted(node_ids)} if node_ids else None`, line 58) — the
    Rust function must likewise return `None` (not `Some` with empty vecs)
    when both the pre-existing graph-traversal extraction and the new hybrid
    extraction yield nothing, matching the existing `if node_ids.is_empty() &&
    edge_ids.is_empty() { None }` branch at lines 111-119.
  - **No `edge_ids` are ever produced by the hybrid path** — this is the one
    place this task's Rust code will structurally differ per-code-path from
    itself: the pre-existing `edge_id` payload key (graph-traversal
    retrievers) still populates `edge_ids`; hybrid items never do, matching
    Python having no equivalent concept.
- **RRF formula** (`hybrid/ranking.py:19,34,51-52`, exact constants, already
  locked for P1-07 but restated here since ranking tests are ported in
  this task): `rrf_k = max(30, min(60, 20 + 2 * chunks_top_k))`;
  `rrf_score = Σ 1.0 / (rrf_k + rank + 1)` over each non-`None` rank in
  `(bm25_rank, vector_rank, summary_rank)`.
- **Importance factor** (`hybrid/ranking.py:55-59`): `importance =
  clamp(payload.get("importance_weight", 0.5), 0.0, 1.0)`;
  `factor = 0.75 + 0.5 * importance` (range `[0.75, 1.25]`). Only applied when
  `use_importance_weight` is true (default `true` per `HybridRetriever.__init__`,
  `hybrid_retriever.py:51`). `importance_weight` lives on `DataPoint`
  (Python-faithful, per locked decision (3)) — confirm the Rust `DataPoint`
  equivalent from P1-0x already exposes it before writing the importance
  fixtures.
- **Sort/tie-break key** (`hybrid/ranking.py:47`):
  `sort by (-final_score, -rrf_score, min(ranks), chunk_id)` ascending — i.e.
  highest final score first, ties broken by highest raw RRF score, then by
  lowest (best) individual channel rank, then lexicographically by
  `chunk_id` string as the last deterministic tie-breaker. Port this exact
  4-tuple ordering, not just the score.
- **Entity edge dedupe/type-pin** (`hybrid/entities.py:130-171,204-221`):
  dedupe key is `(source_id, relationship, target_id)` when all three are
  present, else falls back to exact bullet-text dedupe; sort key is
  `(0, 0)` for "is a"/type edges (pinned first), `(1, rank)` for edges whose
  recomputed `edge_type_id` appears in the `EdgeType_relationship_name` query
  hits (`edge_rank_by_id`, `hybrid/facts.py:28-34` — first-occurrence rank
  only, ties keep the earliest hit), `(2, 0)` for unranked edges (stable
  legacy graph order last).
- **Fact gating** (`hybrid_retriever.py:200-211`, `hybrid/facts.py:37-54`):
  facts are **entirely disabled** when `facts_top_k <= 0` **or** `node_name`
  (the node-set filter) is set — comment: "EdgeType rows carry no node-set
  fields", so scoped searches cannot safely surface facts. `MIN_FACT_WORD_COUNT
  = 3` (facts.py:7) — any candidate fact text with fewer than 3 whitespace-
  split words is dropped. `bullet_ids` (edges already surfaced as entity
  bullets) are excluded from facts via `edge_type_id` match, so a fact never
  duplicates a bullet already shown. `CONTAINS_FACT_PREFIX = "Document chunk
  mentions "` (facts.py:10) triggers a text rewrite: strip the prefix and
  upper-case the first remaining character.
- **BM25 lane** (locked decision (5), restated for the retriever-level test in
  step 8): the corpus for BM25 scoring must be rebuilt **per query call**
  inside the hybrid chunk lane, not reused from the existing
  `OnceCell`-cached lexical-retriever corpus — confirm whatever P1-03 wired in
  does not accidentally share that cache when writing the Mock-backed
  integration test, since a stale/shared corpus would make the test flaky
  across repeated calls in the same process.
- **Structural, not bit-identical, parity** (locked decision (2)): the
  ported unit tests assert exact values (since they reproduce Python's exact
  arithmetic on identical fixture inputs), but the retriever-level Mock test
  and the OpenAI-gated test only need overlapping top-k / same-algorithm
  structural parity — do not assert byte-identical LLM completions.
