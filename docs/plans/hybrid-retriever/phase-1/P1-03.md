# P1-03 — Per-query Okapi BM25 chunk scorer

**Status:** completed

## Goal

Deliver a standalone, Python-faithful Okapi BM25 lexical scorer for
`DocumentChunk` nodes — the "BM25 lane" that `HybridRetriever` will fan out to
alongside the two vector-search lanes. This task ports the real BM25 formula
(`cognee/modules/retrieval/bm25_retriever.py:73-104`) with exact constants
(`k1=1.5`, `b=0.75`) and the `\w+`-lowercase-plus-stopword tokenizer, and the
fail-open contract from `cognee/modules/retrieval/hybrid/chunks.py:112-140`
(`search_bm25_chunks`). It is purely additive — a new module exposing an
internal `bm25_scored_chunks` function — and does not touch the existing
Jaccard `LexicalRetriever` or wire anything into `SearchType`/the retriever
factory; those integrations belong to later hybrid-retriever tasks.

## Prerequisites

- None inside this phase strictly block this task — it only depends on
  `GraphDBTrait::get_filtered_graph_data`, which already exists and is stable.
- Soft dependency: whichever task defines the `HybridRetriever` assembly
  (pairs/ranking, referred to elsewhere in this plan as the "hybrid chunks
  lane" task) will be the first *consumer* of `bm25_scored_chunks`. It should
  land after this task, not before.
- Decision 6 (batched `get_neighborhood(ids, depth)` on `GraphDBTrait`) is
  unrelated to this task — BM25 only reads `DocumentChunk` nodes via
  `get_filtered_graph_data`, never neighborhoods/edges.
- Assumed state: `crates/search` compiles clean on `main` at commit `82310dc`
  (verified below); `cognee-graph`'s `MockGraphDB` (`testing` feature) is
  available as a `[dev-dependencies]` of `cognee-search` for tests.

## Implementation steps

1. **Module skeleton.** Create `crates/search/src/retrievers/bm25.rs`. Add
   `mod bm25;` to `crates/search/src/retrievers/mod.rs` (alongside the other
   `mod` lines, e.g. after `mod base_retriever;`) and a narrow `pub(crate)
   use` of the scoring entry point so it stays an internal API, not a public
   crate export, per the brief.

2. **`DEFAULT_STOP_WORDS` already exists in this crate — reuse it, do not
   re-port.** An identical 66-entry list is already ported from the same
   Python source (`cognee/modules/retrieval/utils/stop_words.py:4-71`, a Python
   `set` literal with **66 entries** — verified: `count=66`, already lowercase)
   and lives at `crates/search/src/utils/resolve_edges_to_text.rs:10-21` as
   `static DEFAULT_STOP_WORDS: LazyLock<HashSet<&'static str>>` (currently
   module-private, all 66 tokens in the same order as the Python source).
   Prefer reusing that single list over introducing a second copy: promote it
   to `pub(crate)` (and, if desired, relocate it to a small shared module such
   as `crates/search/src/utils/stop_words.rs` re-exported for both callers) and
   `use` it from `bm25.rs`, so the BM25 lane and `resolve_edges_to_text` can
   never drift apart. **Editing `resolve_edges_to_text.rs` for a visibility
   bump is permitted** (it is not `LexicalRetriever`, whose no-diff constraint
   is a separate checkpoint). If reuse proves awkward, a local duplicate `const
   DEFAULT_STOP_WORDS: &[&str] = &[...]` + its own `LazyLock<HashSet<&'static
   str>>` is an acceptable fallback, but the two lists must then be kept
   byte-for-byte identical. Either way this is a static wordlist, **not** the
   per-query corpus cache decision 5 forbids reusing. (`LazyLock` is std and
   stable on the workspace's `rust-version = "1.91"`; no new dependency
   needed — do not reach for `once_cell` here, std suffices.)

3. **Port the tokenizer.** Source: `tokenize_words` in
   `cognee/modules/retrieval/lexical_retriever.py:15-23` —
   `re.findall(r"\w+", text.lower())` then filter tokens in `stop_words`.
   Rust's `regex` crate is already a `cognee-search` dependency
   (`crates/search/Cargo.toml` — `regex = "1"`). Use `Regex::new(r"\w+")`
   (compiled once via `LazyLock`) against the **lowercased** input string,
   collecting `Match::as_str().to_string()` for every match not in the
   stopword set. Rust's `\w` in the `regex` crate is Unicode-aware by
   default, same as Python 3's `re` default `\w` — no divergence expected.
   Do **not** reuse `LexicalRetriever::tokenize`
   (`lexical_retriever.rs:56-77`): that hand-rolled char-by-char scanner is a
   manual reimplementation for the Jaccard retriever; the BM25 module gets
   its own small tokenizer function so it has no `LexicalRetriever`
   field/lifetime dependency.

4. **Corpus loader (per-query, no cache).** Add a private async fn, e.g.
   `async fn load_chunk_corpus(graph_db: &dyn GraphDBTrait) ->
   GraphDBResult<Vec<(Option<Uuid>, Value, Vec<String>)>>`, that mirrors
   `LexicalRetriever::load_document_chunks`
   (`lexical_retriever.rs:142-175`): build the same
   `HashMap::from([(Cow::Borrowed("type"), vec![json!("DocumentChunk")])])`
   filter, call `graph_db.get_filtered_graph_data(&filters).await?`, re-check
   `node_data["type"] == "DocumentChunk"` (the filter widens to any of the
   given values, so this second check is still required, matching
   `lexical_retriever.rs:151-157`), skip nodes with no `text` field
   (`lexical_retriever.rs:159-161`), and tokenize each chunk's text with step
   3's tokenizer, dropping chunks that tokenize to zero tokens.
   **Divergence from `LexicalRetriever`:** do not store the result behind a
   `OnceCell`/cache field (`lexical_retriever.rs:31` `cached_chunks:
   OnceCell<Vec<CachedChunk>>`, `:177-201` `ensure_initialized`) — decision 5
   requires this function to run its `get_filtered_graph_data` call fresh on
   every `bm25_scored_chunks` invocation, matching Python's
   `BM25ChunksRetriever` which is constructed fresh per search
   (`cognee/modules/retrieval/hybrid/chunks.py:122`:
   `retriever = BM25ChunksRetriever(top_k=limit, with_scores=True)` — a new
   instance every call, so its `initialize()` always rebuilds `self.chunks`
   from scratch too).
   **Payload `id` parity:** Python's `initialize()` does
   `document_id = str(document.get("id") or chunk_id); document.setdefault("id",
   document_id)` (`lexical_retriever.py:76-77`) so the returned payload always
   carries an `"id"` field even on backends that omit it (kuzu, per the
   inline comment on `lexical_retriever.py:74-75`). The existing Rust
   `LexicalRetriever::load_document_chunks` does **not** do this — it computes
   `item_id` for `SearchItem.id` but leaves `payload` as the raw serialized
   `node_data` (`lexical_retriever.rs:163-171`). Port Python's behavior here:
   after resolving `item_id` (payload `"id"` field parsed as UUID, falling
   back to the graph `node_id`), if the payload's `"id"` key is absent or not
   a string, insert `payload["id"] = item_id.to_string()` (or the raw
   `node_id` string if `item_id` is `None`) before returning it. This keeps
   downstream hybrid pairing (Python's `pairs.py`/`ranking.py`, ported in a
   later task) able to key chunks by `payload["id"]` uniformly.

5. **Corpus statistics.** Port `_build_corpus_stats`
   (`bm25_retriever.py:73-87`): given the loaded `(id, payload, tokens)`
   triples, compute:
   - `total_chunks = corpus.len()`
   - `total_length: usize = sum of tokens.len()` across all chunks
   - `avg_chunk_length: f64 = if total_chunks == 0 { 0.0 } else { total_length
     as f64 / total_chunks as f64 }`
   - document frequency `df: HashMap<&str, usize>` — for each chunk, iterate
     its **unique** tokens (`tokens.iter().collect::<HashSet<_>>()`) and
     increment `df[token]` once per chunk that contains it (not per
     occurrence) — this mirrors `for token in set(tokens): document_frequency[token]
     += 1` (`bm25_retriever.py:80-81`).
   - `idf: HashMap<String, f64> = df.iter().map(|(token, df)| (token.clone(),
     (1.0 + (total_chunks as f64 - *df as f64 + 0.5) / (*df as f64 +
     0.5)).ln()))` — exact port of `bm25_retriever.py:84-87`. Use `f64` for
     the accumulation math (Python `float` is f64) even though `SearchItem.score`
     is `f32` — cast down only at the final score, to avoid compounding
     precision drift across many `idf` lookups.

6. **Scorer.** Port `_scorer` (`bm25_retriever.py:89-104`) as a free function
   `fn bm25_score(query_tokens: &[String], chunk_tokens: &[String], idf:
   &HashMap<String, f64>, avg_chunk_length: f64, k1: f64, b: f64) -> f64`:
   - Return `0.0` if `query_tokens.is_empty() || chunk_tokens.is_empty() ||
     avg_chunk_length == 0.0` (`bm25_retriever.py:91`).
   - Build `term_frequencies: HashMap<&str, usize>` via a `Counter`-equivalent
     over `chunk_tokens` (`Counter(chunk_tokens)`, `bm25_retriever.py:94`).
   - `length_norm = k1 * (1.0 - b + b * chunk_tokens.len() as f64 /
     avg_chunk_length)` (`bm25_retriever.py:95`).
   - Iterate the **unique set** of `query_tokens`
     (`for token in set(query_tokens)`, `bm25_retriever.py:98`) — this is the
     "sum over unique query terms" locked decision. For each unique query
     token with `tf = term_frequencies.get(token).copied().unwrap_or(0)`,
     skip if `tf == 0` (`bm25_retriever.py:100-101`), else accumulate `idf +
     (tf * (k1 + 1)) / (tf + length_norm)` using `idf.get(token).copied()
     .unwrap_or(0.0)` for unseen tokens (`bm25_retriever.py:102`, matching
     Python's `self.idf.get(token, 0.0)`).
   - `k1 = 1.5`, `b = 0.75` are compile-time constants
     (`const BM25_K1: f64 = 1.5; const BM25_B: f64 = 0.75;`), not
     configurable parameters — Python's constructor exposes `k1`/`b` args
     (`bm25_retriever.py:23-24`) but every call site in `chunks.py` uses the
     defaults, and the brief locks these exact constants (see Risks).

7. **`bm25_scored_chunks` entry point.** Signature:
   `pub(crate) async fn bm25_scored_chunks(graph_db: &Arc<dyn GraphDBTrait>,
   query: &str, limit: usize) -> Vec<(Value, f32)>` — note this returns a
   plain `Vec`, **not** a `Result`: mirror the fail-open contract of
   `search_bm25_chunks` (`cognee/modules/retrieval/hybrid/chunks.py:112-140`)
   internally rather than surfacing errors to the caller:
   - If `limit == 0`, return `vec![]` immediately (`chunks.py:118-119`).
   - Tokenize `query` with step 3's tokenizer; if empty, return `vec![]`
     (mirrors `LexicalRetriever.get_retrieved_objects`'s `if not query_tokens`
     early return, `lexical_retriever.py:106-108`, reached transitively via
     `retriever.get_retrieved_objects(query)` at `chunks.py:123`).
   - Call step 4's loader. On `Err(_)`, `tracing::warn!` with the error
     (mirrors `logger.warning("BM25 chunk retrieval failed; using vector
     chunks only: %s", error)`, `chunks.py:126-128`, which is Python's
     catch-all `except Exception`; the narrower `except NoDataError: return
     []` at `chunks.py:124-125` has no exact Rust equivalent since
     `get_filtered_graph_data` doesn't distinguish "no data" from other
     failures — collapse both into the same warn-and-empty path) and return
     `vec![]`.
     - Also treat an empty corpus (loader returns `Ok(vec![])`, e.g. no
       `DocumentChunk` nodes) as `vec![]` with no warning — this is the
       normal "empty graph" case, not a failure (parallels
       `LexicalRetriever.get_retrieved_objects`'s `if not self.chunks:
       logger.warning(...); return []`, `lexical_retriever.py:96-98` — Python
       does warn here, so a `tracing::debug!` or `tracing::warn!` is
       reasonable parity; either level is acceptable, prefer `debug!` to
       avoid noisy warnings on legitimately-empty datasets since this path
       runs per query).
   - Build corpus stats (step 5), score every chunk (step 6), sort
     descending by score (ties broken arbitrarily — Python's `heapq.nlargest`
     is not guaranteed stable either, `lexical_retriever.py:122`), truncate to
     `limit` (mirrors `nlargest(self.top_k, ...)`, where `self.top_k` was
     constructed as `limit` at `chunks.py:122`:
     `BM25ChunksRetriever(top_k=limit, with_scores=True)`).
   - **Drop hits with `score <= 0.0`** (`chunks.py:133-134`:
     `if score <= 0: continue`) — apply this filter to the final truncated
     list, matching the order of operations in Python (`nlargest` truncates
     first at `top_k`, then `search_bm25_chunks` filters non-positive scores
     out of that truncated set — so a query that only weakly matches may
     return fewer than `limit` results, or zero).
   - Return `Vec<(Value, f32)>` of `(payload, score as f32)` pairs, `Value`
     being the enriched payload from step 4 (with `"id"` guaranteed present).
   - **Not** ported in this task (left for the hybrid-assembly task that
     consumes this function): `node_name`/`node_name_filter_operator`
     filtering (`chunks.py:137`:
     `payload_matches_node_filter(chunk, node_name, node_name_filter_operator)`)
     and the `candidate_limit = max(0, chunks_top_k * 2)` doubling
     (`chunks.py:41`) — both are caller concerns; `bm25_scored_chunks` takes
     `limit` as given and does not know about node-name scoping. Document
     this explicitly in the function's doc comment so the future caller does
     not assume node filtering already happened.

8. **No `SearchRetriever` impl.** This task does not implement
   `SearchRetriever` or register a new `SearchType` variant. Note: a
   `HybridCompletion` variant **already exists** in
   `crates/search/src/types/search_type.rs` (line 23, enum spans lines 6-24) —
   it was added by P1-01 (already landed on this branch). This task neither
   adds a new variant nor wires `bm25_scored_chunks` into any retriever/factory
   dispatch for `HybridCompletion`; that wiring belongs to the later
   hybrid-assembly tasks (P1-07/P1-09). `bm25_scored_chunks` is a plain async
   function other search code will call directly, matching the brief's
   "internal API" framing.

## Parity notes

- **Formula** (`bm25_retriever.py:95,103`):
  `score = Σ_{t ∈ unique(query_tokens)} idf(t) · (tf(t,c) · (k1+1)) / (tf(t,c)
  + k1·(1 − b + b·|c|/avgdl))`, computed only over query tokens with `tf > 0`
  in the chunk.
- **IDF** (`bm25_retriever.py:85`): `idf(t) = ln(1 + (N − df(t) + 0.5) /
  (df(t) + 0.5))` — note the Okapi-BM25-with-Robertson-Sparck-Jones-floor
  variant (the `1 +` inside the `ln`), not the classic unclamped BM25 IDF
  that can go negative for very common terms. Do not "improve" this to the
  classic formula — bit-for-bit constant/formula match is the acceptance bar
  (decision 1).
- **Constants**: `k1 = 1.5`, `b = 0.75` (`bm25_retriever.py:23-24` defaults —
  hardcode, do not expose as params in this task, decision-locked).
- **Stop words**: 66-entry list, verified against
  `cognee/modules/retrieval/utils/stop_words.py:4-71`. Case: Python compares
  lowercase tokens against a set that is already all-lowercase; port
  verbatim, no case-folding surprises.
- **Tokenizer**: `\w+` on the lowercased string. Rust `regex` crate's `\w` is
  Unicode-aware (same as Python 3 `re` default) — exotic Unicode edge cases
  (combining marks, some scripts) are an accepted risk under the ~50%
  structural-tolerance bar (decision 2), not something to chase to
  bit-parity.
- **Corpus scope**: rebuilt **fresh per query** (decision 5) — no
  `OnceCell`/process-lifetime cache, unlike `LexicalRetriever`
  (`lexical_retriever.rs:31`). This is intentionally less efficient than the
  Jaccard retriever's caching; see Risks for the follow-up.
- **id scheme**: chunk payload `"id"` is always populated (backfilled from
  the graph node id when absent), per `lexical_retriever.py:76-77`. UUID
  parsing follows existing convention (UUID v5 content-addressed ids are
  already assigned upstream by ingestion — this task only *reads* ids, it
  does not mint any).
- **Score type**: Python scores are Python `float` (f64); Rust `SearchItem`
  and this task's return tuple use `f32` for the final external value (to
  match `SearchItem.score: Option<f32>` at `search_result.rs:12`), but all
  intermediate accumulation (idf, length_norm, score sum) should be done in
  `f64` to minimize divergence before the final narrowing cast — this is a
  deliberate, documented divergence point for the acceptance harness (exact
  score value is not the bar; overlapping top-k ranking is, per decision 2).
- **Fail-open**: any corpus-load error → warn + `vec![]`; empty corpus (no
  chunks, or all-empty-after-tokenizing) → `vec![]` with no error (mirrors
  `chunks.py:124-128` and `lexical_retriever.py:96-98`).
- **score <= 0 drop**: applied to the truncated (post-`limit`) result set,
  exactly mirroring `chunks.py:130-139`'s iteration order — do not filter
  before truncating, or a query with many zero-score chunks would return
  fewer results than Python for the same corpus/query in ways that don't
  match.
- **Explicitly out of scope for this task** (left to the hybrid-assembly
  task): `node_name`/`node_name_filter_operator` filtering
  (`chunks.py:137`), the `chunks_top_k * 2` candidate-limit doubling
  (`chunks.py:41`), and any `use_truth_weight`/`build_truth_subspace`
  Phase-2 wiring (decision 4 — those knobs don't touch the BM25 lane at all;
  they affect `rank_chunk_summary_pairs`).

## Testing

Add `crates/search/tests/bm25_retriever.rs` (integration test, using
`MockGraphDB` from `cognee-graph` `testing` feature — already a pattern in
`crates/search/src/retrievers/lexical_retriever.rs:275-468`'s inline test
module; the new tests can either live inline in `bm25.rs` under `#[cfg(test)]`
following that same convention, or as a separate integration test file —
prefer inline unit tests for the pure-math pieces (tokenizer, idf, scorer) and
a small integration test file for the `MockGraphDB`-backed end-to-end path,
matching how `lexical_retriever.rs` mixes both).

1. **Tokenizer unit test**: given `"The Rust Book, 2nd Edition!"` with default
   stop words, asserts `["rust", "book", "2nd", "edition"]` (`"the"` dropped).
2. **IDF/corpus-stats unit test**: a 3-chunk synthetic corpus with known token
   counts; assert `avg_chunk_length` and at least one token's `idf` match a
   hand-computed value (e.g. a token present in 1 of 3 chunks: `idf = ln(1 +
   (3 - 1 + 0.5)/(1 + 0.5)) = ln(1 + 2.5/1.5) = ln(2.6667) ≈ 0.9808`).
3. **Scorer unit test**: reproduce the classic BM25 property that a chunk
   with higher term frequency but the same length scores higher than one
   with lower term frequency (monotonicity in `tf`), and that a longer chunk
   with the same `tf` scores lower than a shorter one (length normalization
   working).
4. **Rare term outranks common term**: a corpus where one query term appears
   in every chunk (df = N, idf ≈ small) and another appears in only one chunk
   (df = 1, idf large) — assert the chunk matching the rare term ranks above
   an equal-tf chunk matching only the common term. This is the key
   regression guard distinguishing BM25 from a Jaccard fallback.
5. **`score <= 0` drop**: a query whose tokens don't appear in a given chunk
   at all should have that chunk absent from the returned vector (BM25 with
   `tf = 0` for every query token yields exactly `0.0`, must be filtered).
6. **`limit = 0`**: returns `vec![]` without touching the graph (can assert
   via a `MockGraphDB` that would otherwise error/panic if queried — or just
   assert the returned vec is empty and non-flaky).
7. **Empty corpus (no `DocumentChunk` nodes)**: `MockGraphDB::new()` with no
   nodes added → `bm25_scored_chunks` returns `vec![]`.
8. **Query tokenizes to nothing** (e.g. all stop words): returns `vec![]}`
   even with a non-empty corpus.
9. **Payload `id` backfill**: add a `DocumentChunk` node via `MockGraphDB`
   whose JSON has no `"id"` field (only relying on the graph's own node id);
   assert the returned payload has a non-null `"id"` field populated from the
   graph node id, per the parity note in step 4.
10. **Per-query freshness (no cross-call cache)**: call `bm25_scored_chunks`
    once, then add a new chunk to the same `MockGraphDB`, call again with the
    same query — assert the second call's corpus reflects the new chunk
    (this is the regression guard for decision 5; a cached implementation
    would miss the new chunk).
11. Update `crates/search/src/retrievers/mod.rs` (or wherever the module list
    is asserted, if any workspace-wide "all retriever modules compile"
    smoke test exists) only if adding `mod bm25;` requires it — none is
    expected to be needed beyond the module declaration itself.

## Risks & open items

- **Per-query cost.** Rebuilding the full `DocumentChunk` corpus (graph load
  + tokenize + df/idf) on every single hybrid search call is O(corpus size)
  per query, unlike the Jaccard `LexicalRetriever`'s process-lifetime cache.
  This is an explicit, accepted tradeoff (decision 5) for correctness/data
  freshness. If this proves too slow in practice, a follow-up task should
  consider a request-scoped or TTL'd cache — out of scope here.
- **No `NoDataError` distinction in Rust.** Python's `search_bm25_chunks`
  special-cases `NoDataError` vs. generic `Exception` (`chunks.py:124-128`).
  `GraphDBTrait::get_filtered_graph_data` returns a single `GraphDBError`
  type with no "no data" variant, so this task collapses both Python
  branches into one warn-and-empty path. Document this in the module's
  rustdoc; revisit only if a concrete case needs to distinguish "backend
  unreachable" from "backend reachable but empty."
- **`k1`/`b` not configurable.** Locked to defaults per the brief; if a later
  phase needs per-tenant tuning, threading them through
  `bm25_scored_chunks`'s signature is a small, additive change — not
  anticipated to require touching this task's internals.
- **Node-name filtering ownership.** `payload_matches_node_filter` semantics
  (`chunks.py:137`) are deliberately not ported here since the brief's
  `bm25_scored_chunks(query, limit)` signature has no `node_name` parameter.
  Whoever writes the hybrid-assembly task must apply that filter on the
  returned payloads themselves, or this task's signature will need revisiting
  before that integration lands.
- **Tokenizer duplication.** This task intentionally does not refactor
  `LexicalRetriever::tokenize` (`lexical_retriever.rs:56-77`) to share code
  with the new BM25 tokenizer, even though both ultimately implement "lowercase
  + word-boundary split + stopword filter" — the existing tokenizer is a
  hand-rolled char scanner (no regex dependency at the time it was written)
  while this task uses the `regex` crate for exact `\w+` parity with Python.
  Unifying them is a reasonable future cleanup but is not this task's job and
  risks destabilizing the existing, already-tested Jaccard retriever.
