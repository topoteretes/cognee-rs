## Goal

Deliver the `HybridRetriever` itself: the `hybrid/` module (`context.rs` for section
formatting and used-id extraction, `mod.rs` for the retriever struct and its
`SearchRetriever` impl), and wiring it into `SearchType` and the standard-retriever
registry. This is the task where the chunk lane (P1-07) and entity/facts lane (P1-08)
are joined into a single `SearchType::HybridCompletion` retriever that produces both a
flat `SearchContext` (for `only_context`/`verbose` responses and downstream
`used_graph_element_ids` extraction) and an LLM completion built from the same
sectioned text Python renders.

   exist from P1-01; skip this step.]** Add the `SearchType::HybridCompletion` variant. In
   `crates/search/src/types/search_type.rs`, insert `HybridCompletion` into the enum
   (position doesn't matter for serde since it's not `#[repr]`-numbered; put it next

2. **Create `crates/search/src/retrievers/hybrid/context.rs`.** Port
   `hybrid/context.py` (verified 77 lines) and `hybrid/entities.py`'s
   `format_entities`/`hybrid/facts.py`'s `format_facts` call sites into two groups of
   functions:
   - `format_passages(chunks: &[ChunkItem]) -> String` — for each chunk, read
     `text` (skip if blank) and an optional per-chunk `summary`; if present emit
     `"[Passage Summary]: {summary}\n[Raw Passage]: {text}"`, else emit `text` alone.
     Join with `"\n---\n"`; prefix `"## Relevant passages\n"`; return `""` if no
     texts survive (Python `hybrid/context.py:61-77`).
   - `format_entities_section(entities: &[EntityItem]) -> String` — per entity, header
     `"### {name} ({type})"` or `"### {name}"` if no type, then description line if
     present, then one `"- {edge_text}"` bullet per edge; entities with a blank name
     are skipped entirely (Python `_format_entity` returns `""` for them,
     `hybrid/entities.py:101-104`). Join entity blocks with
     `"\n\n"`, prefix `"## Relevant entities\n"` (Python `hybrid/entities.py:75-119`).
   - `format_facts_section(facts: &[FactItem]) -> String` — one `"- {text}"` line per
     fact, prefix `"## Related facts\n"` (Python `hybrid/facts.py:65-69`).
   - `format_hybrid_context(global_context: Option<&str>, chunks, entities, facts) ->
     String` — push each non-empty section (`global_context` first if `Some` and
     non-empty, then passages, then entities, then facts) into a `Vec<String>` and
     `.join("\n\n")` (Python `hybrid/context.py:8-30`). Since `include_global_context_index`
     is unsupported in this phase (see Risks), callers always pass `None` for now —
     keep the parameter so the signature doesn't need to change when Phase 3 lands it.
   - `extract_used_ids(chunks, entities) -> Option<UsedGraphElementIds-shaped struct>`
     (or return the two `Vec<String>`/`HashSet<String>` directly — final shape is a
     P1-10 integration decision) that walks chunk ids, entity ids, and each entity's
     edge `source_id`/`target_id`, **skipping facts entirely** — this is the direct
     Rust port of `extract_context_object_ids` (Python `hybrid/context.py:33-58`,
     verified). Facts are excluded because their id is an `EdgeType` vector-row id,
     not a graph node id (Python comment at `hybrid/context.py:34`, preserved
     verbatim as a Rust doc-comment).
   These operate on whatever typed shape P1-07/P1-08 hand back (chunk struct with
   `id`/`text`/`summary`/raw payload; entity struct with `id`/`name`/`description`/
   `type`/`edges: Vec<EdgeBullet{source_id,target_id,relationship,text,edge_type_id}>`;
   fact struct with `id`/`text`) — do not invent a second representation here; reuse
   P1-07's/P1-08's return types directly so this module has no duplicate structs to
   keep in sync.

3. **THE LOAD-BEARING DESIGN — define the `SearchItem` tagging.** `context.rs` (or a
   small private module it re-exports, e.g. `hybrid::items`) must also provide the
   conversion from the four lane outputs into the flat `SearchContext` (`Vec<SearchItem>`)
   that `get_context` returns and that the orchestrator's dataset-scoping and
   `used_graph_element_ids` machinery consume. Concretely, tag every `SearchItem`'s
   JSON payload with a `"kind"` discriminator:
   - **Chunk items** (`"kind": "chunk"`): `item.id = Some(chunk_uuid)` (parsed from
     the chunk's content-hash id string; `None` if unparsable — never `unwrap`).
     `item.payload` starts from the chunk lane's raw vector-metadata JSON object
     (so `dataset_ids`/`dataset_id` survive unmodified for
     `orchestration/dataset_scope.rs`'s `scope_context_by_datasets`, which reads the
     `dataset_ids` array as authoritative membership with a scalar `dataset_id`
     back-compat fallback — verified `crates/search/src/orchestration/dataset_scope.rs:22-46`),
     then has `"kind": "chunk"` and `"chunk_summary": <string or absent>` merged in.
     The summary is carried **on the chunk item itself** (not a parallel map), per
     brief — this is what lets `get_completion`'s reconstruction step avoid needing a
     side channel.
   - **Entity items** (`"kind": "entity"`): `item.id = Some(entity_uuid)` (same
     parse-or-`None` rule). `item.payload` = `{"kind": "entity", "id", "name",
     "description", "type", "edges": [ {"text","source","target","source_id",
     "relationship","target_id","edge_type_id"}, ... ] }` — the `edges` array is
     nested JSON, one object per edge bullet, mirroring Python's
     `entity["edges"]` list of dicts (`hybrid/entities.py:183-201`) verbatim so
     `format_entities_section` and any downstream consumer can walk it without a
     second schema.
   - **Fact items** (`"kind": "fact"`): `item.id = Some(fact_uuid)` parsed from the
     `EdgeType` vector-row id (Python `hybrid/facts.py:37-54`), `item.payload =
     {"kind": "fact", "id", "text"}`. No `source_id`/`target_id`/`edges` — this is
     the field-level contract that lets a "kind"-aware id extractor skip facts
     without special-casing anything else.
   - `get_context` assembles the final `SearchContext` as
     `chunk_items ++ entity_items ++ fact_items` (stable order, chunk lane first to
     match the section order humans read in `format_hybrid_context`).
   - **Contract handed to P1-10**: today's `build_used_graph_element_ids` in
     `crates/search/src/orchestration/search_orchestrator.rs:88-120` only reads
     `source_id`/`target_id`/`edge_id` at the payload's top level — it does not look
     at `item.id`, a top-level `"id"` field, or nested arrays, so it currently
     extracts **nothing** from hybrid's chunk or entity items as-is. P1-10 must add a
     `kind`-aware branch: when `payload["kind"] == "chunk"` or `"entity"`, insert
     `payload["id"]` (or `item.id`) into `node_ids`; when `"entity"`, also walk
     `payload["edges"]` inserting each element's `source_id`/`target_id`; when
     `"kind" == "fact"`, skip the item entirely (do not touch `node_ids`/`edge_ids`).
     This is the Rust-side mirror of `extract_context_object_ids`
     (`hybrid/context.py:33-58`) and is **out of scope for this task** — P1-09 only
     needs to guarantee the tagging contract above is stable so P1-10 can implement
     against it without re-deriving the shape.
   - **`prepare_search_result` compatibility (verified)**: `prepare_search_result`
     itself is item-shape-agnostic (it wraps any `SearchContext` into the
     `context`/`graphs` maps), and its `transform_context_to_graph` helper only
     emits a graph when an item carries **top-level** `source_id` + `target_id` +
     `relationship` payload keys (`crates/search/src/orchestration/prepare_search_result.rs:83-153`).
     Hybrid items carry none of those at top level (entity edges are nested under
     `payload["edges"]`), so hybrid responses get `graphs: None` — nothing breaks,
     and this matches the fact that hybrid's context is section-text-oriented, not
     triplet-oriented. Do not flatten entity edges to top-level `source_id`/`target_id`
     to force a graph: that would also make `build_used_graph_element_ids`' existing
     top-level scan pick up entity edge endpoints *before* P1-10's kind-aware branch
     lands, changing behavior in an uncontrolled order.

     `hybrid_retriever.py:83-85`). Map each lane's typed output into `SearchItem`s
     per step 3's tagging, concatenate, return `Ok(SearchContext)`. Knob resolution
     (mirrors Python's two sources exactly):
     - `node_name` / `node_name_filter_operator` come from the **dedicated
       `SearchParams` fields** (`params.node_name` / `params.node_name_filter_operator`,
       already present at `search_params.rs:31-34`), falling back to the constructor

     prompt via `resolve_system_prompt(params.system_prompt.as_deref().or(self
     .system_prompt.as_deref()), params.system_prompt_path.as_deref().or(self
     .system_prompt_path.as_deref()))` (same call shape as
     `completion_retriever.rs:113-122`; the path-missing fallback logic at
     `crates/search/src/utils/completion.rs:20-39` already resolves a bare

     `render_user_prompt`-style `{question}`/`{context}` substitution. Build messages

     `llm.create_structured_output_with_messages_raw(...)` → `SearchOutput::Structured`;

     `completion_retriever.rs:135-152`).

     query_batch.".to_string()))` (trailing period included — exact Python message

## Parity notes

- **Section order & join**: `format_hybrid_context` joins non-empty sections with
  `"\n\n"` in the order global → passages → entities → facts
  (`hybrid/context.py:8-30`, verified). Passage texts within the passages section
  join with `"\n---\n"` (`hybrid/context.py:77`); entity blocks within the entities
  section join with `"\n\n"` (`hybrid/entities.py:83`); fact lines join with `"\n"`
  and a leading `"- "` each (`hybrid/facts.py:65-69`).
- **Passage Summary format**: exactly
  `"[Passage Summary]: {summary}\n[Raw Passage]: {text}"` when a chunk has a paired
  summary, else the raw text alone (`hybrid/context.py:71-74`).
- **Fact exclusion from used-ids**: `extract_context_object_ids` deliberately does
  not touch `retrieved_objects["facts"]` — the comment at `hybrid/context.py:34`
  states facts are `EdgeType` vector rows, not graph nodes. Preserve this exactly:
  a `"kind": "fact"` `SearchItem` must never contribute to `node_ids`/`edge_ids`.
- **Query-batch rejection message**: Python raises
  `QueryValidationError("HYBRID_COMPLETION does not support query_batch.")` (note the
  trailing period) at `hybrid_retriever.py:301-302`. Use
  `SearchError::InvalidInput("HYBRID_COMPLETION does not support
  query_batch.".to_string())` — no Rust `QueryValidationError` type exists in this
  crate; `InvalidInput` is the established mapping (see `chunks_retriever.rs:64`
  for the same mapping pattern on a different validation failure). Keep the trailing
  period for exact message-text parity (step 5's snippet includes it). This is a
  case where the wrapping *error type* diverges from Python by necessity (no
  dedicated `QueryValidationError` variant in `SearchError`) — the message text
  parity is what's load-bearing for any test asserting on it.
- **Prompt template divergence (accepted)**: Python's on-disk
  `hybrid_context_for_question.txt` uses Jinja-style `{{ question }}`/`{{ context }}`
  placeholders (verified by reading the file). The Rust SDK ships prompts as
  compiled-in constants using single-brace `{question}`/`{context}` `.replace()`
  substitution (matching every existing template — `DEFAULT_RAG_USER_PROMPT_TEMPLATE`,
  `DEFAULT_GRAPH_USER_PROMPT_TEMPLATE` at `crates/search/src/utils/completion.rs:7-9`).
  `DEFAULT_HYBRID_USER_PROMPT_TEMPLATE` (P1-05) must follow the same single-brace
  convention — this is an intentional, already-established Rust-vs-Python mechanism
  divergence (prompts are compiled in, not read from a prompts directory), not a new
  one introduced here.
- **System prompt text parity**: `answer_simple_question.txt`
  ("Answer the question using the provided context. Be as brief as possible.") is
  byte-identical to `DEFAULT_RAG_SYSTEM_PROMPT`
  (`crates/search/src/utils/completion.rs:5-6`) — verified by reading both. No new
  constant needed; `HybridRetriever`'s default `system_prompt_path` resolves to it
  via the existing fallback.
- **Structural, not bit-identical, acceptance bar**: per the locked project decision,
  parity is judged by the e2e-cross-sdk harness pattern in
  `e2e-cross-sdk/harness/test_cognify_structural.py` (verified: node/edge count
  compared with `ratio > 0.5` tolerance, type-set Jaccard `>= 0.3`) — a hybrid
  analogue should compare top-k id overlap and section presence, not exact text.
- **BM25 is P1-07's concern, not this task's**: the chunk lane's ranked pairs already
  blend a real Okapi BM25 pass (`hybrid/chunks.py:43-44` calls
  `search_bm25_chunks` → `BM25ChunksRetriever`) with vector search and summary hits.
  P1-09 treats this as an opaque upstream dependency — it must not reuse the
  existing `LexicalRetriever`'s Jaccard-based `OnceCell`-cached corpus
  (`lexical_retriever.rs:18-30`), and the BM25 corpus for the hybrid lane must be
  rebuilt per-query rather than cached process-lifetime, per the locked decision —
  but implementing that rebuild is P1-07's job.
- **`get_neighborhood` is P1-08's concern, not this task's**: `build_entities`
  (`hybrid/entities.py:15-44`) depends on a batched
  `graph_engine.get_neighborhood(entity_ids, depth=1)` call that returns `(nodes,
  edges)` for the whole entity_ids set in one round trip, with **true stored edge
  direction** (fixing the ladybug backend's undirected direction-flip per the locked
  decision). P1-09 only consumes the `Vec<EdgeBullet>` this produces per entity; it
  does not touch `GraphDBTrait`.

## Risks & open items

- **`include_global_context_index` is unsupported in Phase 1.** No Rust
  `global_context` utility exists (`load_root_text`,
  `search_top_global_context_summaries`, `format_global_context_prelude` all have no
  Rust counterpart — verified by grepping `crates/` for `global_context`, which only
  matches unrelated `remember`/`improve` code). `HybridRetriever` accepts the knob
  (per decision 8, it's on the wire and not rejected) but the "## Global context"
  section is always omitted regardless of the flag's value. This is a documented
  Phase-3-ish limitation, not a bug — a query with `include_global_context_index:
  true` silently gets no global-context section rather than erroring. Consider a
  `tracing::debug!` (not `warn!`, to avoid alarming default users who never set this
  flag) when the flag is `true` but the section ends up empty for this reason.
- **Phase 2 knobs (`use_truth_weight`, `build_truth_subspace`) are wire-visible but
  inert.** `HybridRetriever` must accept and thread these through
  `retriever_specific_config` without erroring, but must not attempt truth-subspace
  alignment (`_build_truth_context`, `_candidate_chunk_ids` in
  `hybrid_retriever.py:110-165`) — no Rust `truth_subspace` module exists yet and
  porting it is explicitly out of Phase 1 scope.
- **Constructor arity.** Step 4's field list is long (16 constructor params); if
  P1-05/P1-07/P1-08 land with slightly different helper names or an extra
  `Options`-struct-style constructor convention, prefer matching whatever pattern
  those tasks establish over a raw positional constructor — this doc specifies the
  *fields*, not necessarily the literal function signature shape.
- **`build_used_graph_element_ids` update is P1-10's responsibility, not this
  task's** — until P1-10 lands, hybrid searches will produce `SearchContext` with
  correctly tagged items, but `used_graph_element_ids` on saved QA session entries
  will stay empty for hybrid searches (same "nothing extracted" behavior as today,
  just not yet improved for the new `"kind"` tags). Not a regression, but worth
  flagging so P1-10 isn't skipped.
- **Existing datasets degrade silently, no backfill** (locked decision 7): datasets
  indexed before this lands have no `EdgeType_relationship_name` collection tuned
  for the facts lane in the way P1-08 expects; `search_collection`'s existing
  `CollectionNotFoundError` → empty-channel fallback (`hybrid/chunks.py:170-175`,
  ported by P1-07/P1-08) already covers this gracefully — just confirm P1-09's lane
  calls don't turn a missing-collection empty result into a hard error anywhere in
  the concurrent `try_join!`.
