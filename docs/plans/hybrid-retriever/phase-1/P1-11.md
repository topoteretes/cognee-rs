## Goal

Wire `HYBRID_COMPLETION` into the `e2e-cross-sdk` Python↔Rust parity harness so the
new retriever is exercised by CI the same way every other `SearchType` is: a
Phase-1 (no-LLM) wire/status-shape check, plus a Phase-2 (LLM-gated) structural
parity check that compares Python's and Rust's hybrid retrieval output within a
cognify-style tolerance rather than requiring byte-identical results. The
structural check must be **context-only** (`only_context=true`) so it never
invokes the completion LLM call and stays deterministic; ranking/formatting from
the chunk, entity, and fact lanes is what is actually being compared.

6. Add structural-tolerance assertions. Because the two `searchResult` shapes
   differ, extract the three structural quantities — `(entity_names: set,
   passage_count: int, fact_count: int)` — from each side with a
   **shape-specific parser**, then compare the extracted quantities (which are
   directly comparable):
   - **Python side (markdown string parser)** — parse the section markers
     `format_hybrid_context` produces
     (`/tmp/cognee-python/cognee/modules/retrieval/hybrid/context.py`,
     `entities.py`, `facts.py` — literals in Parity notes):
     - entity names: regex `^### (.+)$` (MULTILINE), strip a trailing
       `" (Type)"` suffix to get bare names.
     - passage count: under `## Relevant passages`, split the section body on
       the literal separator `\n---\n` and count non-empty parts.
     - fact count: lines starting with `"- "` under `## Related facts`.
   - **Rust side (JSON item-array parser)** — walk `searchResult` (a list of
     `SearchItem` dicts) keyed on `item["payload"]["kind"]` (verified builders:
     `tag_chunk_item`/`entity_to_item`/`fact_to_item`,
     `crates/search/src/retrievers/hybrid/mod.rs:237-297`):
     - entity names: `payload["name"]` for items with `payload["kind"] ==
       "entity"` (bare name; no `(Type)` suffix on the Rust side — do not strip).
     - passage count: count items with `payload["kind"] == "chunk"`.
     - fact count: count items with `payload["kind"] == "fact"`.
   - **Comparisons** (identical tolerance shape to the cognify structural test):
     - **Entity name overlap**: Jaccard similarity of the two bare-name sets
       `>= 0.3`, skipping (not failing) when both sides produced zero entity
       names — same shape as `test_cognify_node_types_overlap`
       (`test_cognify_structural.py:104-123`).
     - **Passage count tolerance**: assert both `> 0` and `warnings.warn(...)`
       (do not fail) if `abs(py_count - rust_count) / avg > 0.5` — same
       warn-only pattern as `test_cognify_node_count_within_tolerance`
       (`test_cognify_structural.py:52-73`).
     - **Fact count tolerance**: same `>0` + 50%-tolerance-warn pattern.
   - Keep both shape-specific parsers as small module-private functions in the
     new test file (e.g. `_extract_from_python_markdown(str) -> tuple` and
     `_extract_from_rust_items(list) -> tuple`, each returning
     `(entity_names, passage_count, fact_count)`) — this is harness-only scope;
     do not add a shared "hybrid context parser" to `helpers.py` unless a
     second test needs it.
   - **Smoke guard against silent 0-parsing**: before trusting the counts,
     assert the Python markdown actually contains at least one of
     `"## Relevant passages"` / `"## Relevant entities"` / `"## Related facts"`,
     and that the Rust array contains at least one item with a recognized
     `kind`. This turns a formatter drift on either side into a hard failure
     rather than a silent "0 entities" Jaccard skip (see Risks).

## Parity notes

- **Context format literals to match** (Python is authoritative; Rust's
  formatter, built in an earlier phase-1 task, must reproduce these exactly
  for the regex-based structural parsers in step 6 to work symmetrically):
  - Passages: header `"## Relevant passages\n"`, passages joined with
    `"\n---\n"` (`hybrid/context.py` `format_passages`).
  - Entities: header `"## Relevant entities\n"`, entity blocks joined with
    `"\n\n"`, each block starts with `"### {name} ({type})"` or `"### {name}"`
    if no type (`hybrid/entities.py:101-119`).
  - Facts: header `"## Related facts\n"`, one `"- {text}"` bullet per line
    (`hybrid/facts.py:63-65`).
  - Sections are joined top-to-bottom with `"\n\n"` in the order: global
    context, passages, entities, facts (`hybrid/context.py:8-29`). Global
    context is omitted by default (`include_global_context_index=False`), so
    the new test never has to parse it.
- **Retriever defaults exercised** (must not be overridden by the test unless
  explicitly noted, so they match Python's constructor defaults,
  `hybrid_retriever.py:36-70`): `chunks_top_k=5`, `entities_top_k=5`,
  `max_edges_per_entity=10`, `text_summaries_top_k=None` (→ defaults to
  `chunks_top_k`), `use_importance_weight=True`, `use_truth_weight=False`,
  `facts_top_k=5`, `include_global_context_index=False`.
- **`importance_weight` default**: Python `DataPoint.importance_weight: float
  | None = 0.5` (`DataPoint.py:75`); Rust does not have this field yet
  (confirmed by reading `crates/models/src/data_point.rs`, which has
  `feedback_weight` with `default_feedback_weight() -> f64 { 0.5 }` at
  `:11-13` and `:87-89` but no `importance_weight`) — this is exactly what
  P1-04 is expected to add. This task does not touch that file; it only
  verifies the fixture-churn blast radius is zero (step 9).
- **`only_context` is already a first-class wire field on both SDKs** — this
  is what makes the context-only design viable without any new production
  code: Rust `SearchPayloadDTO.only_context`
  (`crates/http-server/src/dto/search.rs:110-111`, alias `only_context`,
  wire `onlyContext`) and Python `SearchPayloadDTO.only_context: bool =
  Field(default=False)`
  (`/tmp/cognee-python/cognee/api/v1/search/routers/get_search_router.py:65`).
  Both already thread it through to `get_context_from_objects` /
  `get_retriever_output.py:96-102` (Python) and
  `SearchRequest.only_context()` / `search_orchestrator.rs:399` (Rust),
  skipping the completion call entirely. No wire change needed for this
  mechanism — only the `HYBRID_COMPLETION` enum variant itself is new.
- **only_context output-shape divergence (Rust ≠ Python) — the reason steps
  5-6 use asymmetric parsers.** This is a real, verified, and *accepted*
  cross-SDK difference in how the `searchResult` field is shaped when
  `only_context=true`, and it is NOT specific to the hybrid retriever:
  - **Python**: `get_context_from_objects` returns
    `format_hybrid_context(...)` — the **markdown string** with
    `## Relevant passages` / `## Relevant entities` / `## Related facts`
    sections (`hybrid_retriever.py:213-221`). Because `only_context=true`
    skips completion (`get_retriever_output.py:102`), that markdown string is
    what lands in `searchResult`.
  - **Rust**: the orchestrator's only_context branch
    (`search_orchestrator.rs:399-401`) wraps the retriever's
    `get_context()` output — a `Vec<SearchItem>` (`SearchContext`,
    `crates/search/src/types/search_result.rs:16`) — as
    `SearchOutput::Items(...)`, which `flatten_search_response`
    (`crates/http-server/src/dto/search.rs:245-247`) serializes as a **JSON
    array**. The `format_hybrid_context` markdown is built only inside
    `HybridRetriever::get_completion` (`retrievers/hybrid/mod.rs:448+`), which
    the only_context path never calls. This is a Rust-wide only_context
    representation (structured items for every retriever), orthogonal to
    hybrid, so it is treated as an accepted parity gap and handled in the
    harness rather than "fixed" in production — P1-11 stays harness-only. The
    structural quantities (entity names, passage/fact counts) are equally
    recoverable from both shapes, which is why parity is still assertable.
- **`retriever_specific_config` is NOT on either HTTP wire today.** Rust's
  core `SearchRequest.retriever_specific_config: Option<HashMap<String,
  serde_json::Value>>` exists (`crates/search/src/types/search_request.rs:33-35`)
  but `SearchPayloadDTO` has no matching field, and Python's
  `SearchPayloadDTO` (`get_search_router.py:25-70`) has none either — the
  Python SDK only accepts `retriever_specific_config` as a direct
  `cognee.search()` kwarg, not over HTTP. This means LOCKED DECISION 8
  ("expose all hybrid knobs on the wire") describes a **Rust-side-only**
  wire addition with no Python HTTP counterpart to structurally compare
  against yet. P1-11's structural test therefore exercises only the
  constructor **defaults** (no `retrieverSpecificConfig` in the request body)
  to stay comparable; see Risks.
- **`searchResult` field naming**: `SearchResultDTO` is `#[serde(rename_all =
  "camelCase")]` (`dto/search.rs:200`, field `search_result` at `:202`) so the
  wire key is `searchResult` — confirmed by reading the struct directly, not
  assumed from other DTOs.
- Divergence to accept, not fix: cognify's LLM-driven entity/fact extraction
  is inherently non-deterministic between runs and between SDKs (different
  LLM client code paths, potentially different prompt rendering) — this is
  why acceptance is Jaccard/count-tolerance, identical to the existing
  cognify structural test's rationale (`test_cognify_structural.py:1-6`).

## Risks & open items

- **P1-09 sequencing risk (now landed, but the guard still matters)**:
  `HYBRID_COMPLETION` is wired and the `HybridRetriever` is registered
  (`search_execution_builder.rs:231`), so dispatch is real, not stubbed. The
  guard remains: an empty result (Python `""` / Rust `[]`) must fail loudly
  rather than skip — do not add a lenient empty skip path to this test; an
  empty `searchResult` is a hard failure, distinct from the 404-skip path
  reserved for "endpoint not registered yet". Apply the emptiness check in
  each side's native shape (non-empty string vs non-empty list).
- **`retriever_specific_config` has no Python HTTP counterpart** (see Parity
  notes) — if a later task adds `retrieverSpecificConfig` to Rust's
  `SearchPayloadDTO` only, any harness test that exercises non-default hybrid
  knobs (`chunksTopK`, `factsTopK`, etc.) cannot be a *parity* test until
  Python's HTTP wire gains the same field or the harness falls back to
  Python's SDK-level `cognee.search(..., retriever_specific_config=...)`
  path instead of HTTP for that one comparison. Deferred; not part of this
  task's acceptance bar.
- **Silent 0-parsing on either side** — because the two sides are parsed in
  different shapes (Python markdown regex, Rust `payload["kind"]` walk), a
  formatter/shape drift on one side would read as "0 of everything" and let
  the Jaccard check silently skip rather than error. This is why step 6
  mandates a smoke guard: the Python markdown must contain at least one of the
  three section headers, and the Rust array must contain at least one item
  with a recognized `kind`, before the counts/Jaccard are trusted. NOTE: the
  Rust side does NOT depend on markdown markers in only_context (it never emits
  them there — see the divergence note); it depends only on the
  `{kind, name, text}` payload keys, verified against
  `entity_to_item`/`fact_to_item`/`tag_chunk_item`
  (`retrievers/hybrid/mod.rs:237-297`). The Rust markdown formatter fidelity
  (`## Relevant passages`, `### {name}`, `## Related facts`) is confirmed
  present in `retrievers/hybrid/{context,entities,facts}.rs` but is only
  exercised on the completion path, which this test does not hit.
- **`use_truth_weight`/Phase-2 knobs are out of scope for this harness task**
  by design (LOCKED DECISION 4: default-off, deferred execution) — no test
  here exercises them; a future phase-2 task doc should add a dedicated
  truth-subspace structural test once `build_truth_subspace` ships.
- **CI cost**: the new Phase-2 test adds one more `add + cognify` round trip
  per SDK (two LLM entity-extraction calls) to an already LLM-gated job;
  acceptable since it reuses the existing Phase-2 lane rather than adding a
  new CI job, but worth noting if Phase-2 wall-clock time becomes a concern.
