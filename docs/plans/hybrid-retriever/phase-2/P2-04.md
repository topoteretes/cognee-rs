# P2-04 — Truth-subspace: graph truth-state methods

**Status:** completed

## Goal

Add a `GraphDBTrait` extension point for reading and writing per-node
"truth-subspace" state (`truth_alignment` coordinates + `truth_epoch`
version stamp) so that the (deferred) truth-subspace builder can persist
centroid-alignment scores on chunks/entities, and the hybrid retriever's
truth-weighting lane can read them back. This task delivers only the
trait surface (default impl + three backend overrides); it does not wire
up any caller. It unblocks P2-06 (write path: `build_truth_subspace`
persisting scored nodes) and P2-07 (read path: hybrid ranking consuming
truth state), both of which stay behind the default-off
`use_truth_weight` / `build_truth_subspace` knobs.

- None beyond what is already on `main`: the `feedback_weight` trait
  methods (`get_node_feedback_weights` / `set_node_feedback_weights`)
  already exist on `GraphDBTrait` and are the template this task follows.
- No other P2-xx task needs to land first. This task is a leaf: it only
  touches `crates/graph`.
- Assumed state: `crates/graph` compiles today with `ladybug` and
  `postgres` cargo features available, and `MockGraphDB` gated behind
  `#[cfg(any(test, feature = "testing"))]` in `crates/graph/src/lib.rs`.

## Implementation steps

1. **Define `NodeTruthState`** in `crates/graph/src/traits.rs`, next to
   the existing `EdgeKey` type alias (line 15):
   ```rust
   /// Per-node truth-subspace alignment state: coordinates against the
   /// current centroid slots plus the epoch they were computed against.
   #[derive(Debug, Clone, PartialEq, Default)]
   pub struct NodeTruthState {
       pub truth_alignment: Vec<f64>,
       pub truth_epoch: i64,
   }
   ```
   Use `i64` (not `Option<i64>`) for `truth_epoch` per the locked
   signature — see Parity notes for how "no epoch yet" is represented.

2. **Default `get_node_truth_state`** — insert immediately after
   `set_node_feedback_weights` (line 421). Loop over `node_ids`, call
   `self.get_node(id).await?` per id (same shape as
   `get_node_feedback_weights`, lines 388–401). For each **found** node
   (i.e. `get_node` returns `Some`):
   - Read `truth_alignment`: if the property is a JSON array, map each
     element through `.as_f64()`, defaulting any non-numeric element out
     (skip it) — otherwise (missing / wrong type) use `vec![]`.
   - Read `truth_epoch`: accept either a JSON number (`.as_i64()`) or a
     numeric string (`.as_str()` then `str::parse::<i64>()`), matching
     Python's tolerance for stringly-typed epoch values (see Parity
     notes). If absent or unparseable, use the sentinel `-1`.
   - Insert `(id.clone(), NodeTruthState { truth_alignment, truth_epoch })`
     into the output map **unconditionally when the node exists** — unlike
     `get_node_feedback_weights`, which omits nodes missing the property,
     this method includes every found node with defaulted fields. This
     mirrors the Python behavior where `get_node_truth_state` only excludes
     node ids absent from the graph, never ones merely missing the
     property (see Parity notes / python:2320-2343).
   - Nodes for which `get_node` returns `None` are omitted from the map
     (silently — no error), matching the existing feedback-weight default.

3. **Default `set_node_truth_state`** — takes
   `&HashMap<String, NodeTruthState>`, returns
   `GraphDBResult<HashMap<String, bool>>`. For each `(id, state)`, call
   `self.update_node_property(id, "truth_alignment", json!(state.truth_alignment)).await`
   and then `self.update_node_property(id, "truth_epoch", json!(state.truth_epoch)).await`;
   the entry is `true` only if **both** calls succeed. This is the same
   "loop + `update_node_property` per id" template as
   `set_node_feedback_weights` (lines 408–421), extended to two
   properties per node since truth state has two fields. Document in the
   rustdoc that the base-trait default costs two `update_node_property`
   round-trips per id (each of which may itself be a full delete+re-add
   cycle on backends that don't override `update_node_property`, per the
   comment on `update_node_property` at lines 318–321) and that backends
   should override for efficiency — exactly as the doc comment on
   `set_node_feedback_weights` already states.

4. **Re-export** `NodeTruthState` from `crates/graph/src/lib.rs`: change
   line 40 to
   `pub use traits::{EdgeKey, GraphDBTrait, GraphDBTraitExt, NodeTruthState};`.

5. **Ladybug batch override** (`crates/graph/src/ladybug.rs`, after line
   1695, before `get_edge_feedback_weights` at 1697). Mirror the existing
   `get_node_feedback_weights` shape (lines 1644–1680):
   - `get_node_truth_state`: build one `MATCH (n:Node) WHERE n.id IN
     [...] RETURN n.id AS id, n.properties AS properties` query (same
     id-list escaping helper used at lines 1651–1655), parse each row's
     `properties` JSON blob (via `sanitize_json_control_chars` +
     `serde_json::from_str`, as in lines 1670–1672), then apply the same
     `truth_alignment` (array→`Vec<f64>`, default `[]`) and `truth_epoch`
     (number-or-numeric-string→`i64`, default `-1`) extraction as step 2.
     Include an entry for **every row returned** (i.e. every node that
     exists), not just ones with the property present.
   - `set_node_truth_state`: keep the same "loop + `update_node_property`
     per id" shape as the existing `set_node_feedback_weights` override
     (lines 1682–1695) — Ladybug's `update_node_property` (lines
     1549–1590) already does an in-place JSON-merge SET rather than a
     delete+re-add, so two calls per id is cheap here; a single-query
     `UNWIND` batched write (as Python's `_execute_node_truth_state_updates`
     does at adapter.py:2217-2232) is a nice-to-have, not required for
     this task — call it out as a follow-up in Risks if skipped.

6. **Postgres batch override** (`crates/graph/src/pg_graph_adapter.rs`,
   inside the `impl GraphDBTrait for PgGraphAdapter` block, e.g. near
   `get_nodes` at lines 526–544):
   - `get_node_truth_state`: call `self.get_nodes(node_ids).await?`
     (existing batched `SELECT ... WHERE id IN (...)` at lines 526–544,
     which already merges the `properties` JSONB column into the
     returned `NodeData` map per `parse_node_row`, lines 281–305), then
     apply the same extraction logic as step 2 to each returned
     `NodeData`. Every id present in the `get_nodes` result gets an
     entry (existence == returned by the query); ids absent from the
     result are omitted.
   - `set_node_truth_state`: call `self.get_nodes(&ids).await?` to fetch
     the current full property maps for all requested ids in one
     round-trip, merge `truth_alignment`/`truth_epoch` into each node's
     JSON map in memory, then call `self.add_nodes_raw(merged).await?`
     (existing batched upsert at lines 424–475, which uses
     `INSERT ... ON CONFLICT (id) DO UPDATE` on `GNode::Properties` and
     does **not** touch the edge table, so unlike the default's
     delete+re-add it never risks dropping edges). Return `true` for
     every id that was present in the `get_nodes` fetch (and thus
     included in the upsert batch), `false` for ids not found in the
     graph. This is more efficient than looping
     `update_node_property` (which on this adapter falls back to the
     expensive default delete+re-add per property, per step 3's note),
     and is the pattern to prefer here.

7. **Mock override** (`crates/graph/src/mock.rs`, inside
   `impl GraphDBTrait for MockGraphDB`): implement both methods as direct
   `HashMap<String, NodeData>` reads/writes under the existing
   `self.nodes` mutex (no need to route through `update_node_property`,
   since the mock already holds nodes as flat property maps — see
   `add_node_raw` at line 102 and `get_node` at line 140). Push
   `"get_node_truth_state"` / `"set_node_truth_state"` onto
   `self.call_log` on each call, following the existing pattern used for
   `get_graph_data` / `get_nodeset_subgraph` (documented on
   `get_call_log`), so P2-06/P2-07 tests can assert call order/arity
   against the mock without needing a real backend.

8. Run `cargo check --all-targets`, then `cargo check --all-targets
   --no-default-features --features ladybug` and `--features postgres`
   individually if the crate's default features don't already cover
   both, to confirm both backend overrides compile under their feature
   gates.

## Parity notes

- **Python source of truth**: trait declaration
  `cognee/infrastructure/databases/graph/graph_db_interface.py:653-667`
  (`get_node_truth_state` / `set_node_truth_state`, both raising
  `NotImplementedError` by default — Python has no generic default impl,
  only per-adapter overrides). Ladybug implementation:
  `cognee/infrastructure/databases/graph/ladybug/adapter.py:2320-2343`
  (get) and `:2345-2359` (set), backed by helpers
  `_build_node_truth_state_updates` (`:2192-2215`) and
  `_execute_node_truth_state_updates` (`:2217-2232`).
- **Inclusion rule (exact parity)**: Python's `get_node_truth_state`
  fetches via `get_nodes(valid_node_ids)` and emits an entry for **every
  node returned** (i.e. every node that exists in the graph), defaulting
  `truth_alignment` to `[]` and `truth_epoch` to `None` when the
  properties are absent or malformed — it does **not** skip nodes
  lacking the property, unlike `get_node_feedback_weights`
  (`:2285-2302`), which defaults missing/invalid `feedback_weight` to
  `0.5` per-node rather than omitting the node either. Verified against
  `cognee/tests/unit/infrastructure/databases/graph/test_ladybug_truth_state.py:26-39`,
  where a node with `truth_alignment: "bad", truth_epoch: "bad"` still
  appears in the result as `{"truth_alignment": [], "truth_epoch": None}`.
  The Rust default and both backend overrides must replicate "present in
  the graph ⇒ present in the output map, with defaulted fields" — this
  is the one behavioral divergence from the existing
  `get_node_feedback_weights` doc comment ("IDs missing the property are
  omitted"), so update `get_node_truth_state`'s own rustdoc to state the
  weaker/different guarantee explicitly rather than copy-pasting the
  feedback-weight wording.
- **Epoch type divergence (accepted)**: Python's `truth_epoch` is
  `Optional[int]` — `None` means "never scored". The locked Rust
  signature uses non-optional `i64`. Represent "never scored" with the
  sentinel **`-1`**, not `0`, because `0` is a legitimate real epoch:
  `build_truth_subspace` (`cognee/modules/truth_subspace/build.py:119,142`)
  seeds `previous_epoch = max(..., default=0)`, i.e. epoch `0` is the
  first real epoch before any increment. `-1` never collides since
  Python epochs are always `>= 0`. Callers in P2-07 must treat `-1`
  (not `0`) as "no truth state yet" and fall back to unweighted scoring.
  Document this sentinel prominently in the `NodeTruthState` rustdoc.
- **Numeric string tolerance**: Python's `int(epoch) if epoch is not
  None else None` inside a `try/except (TypeError, ValueError)` accepts
  a stringly-typed epoch (e.g. `"3"` → `3`) and falls back to `None` on
  garbage (e.g. `"bad"`) — see
  `ladybug/adapter.py:2338-2341` and the matching test at
  `test_ladybug_truth_state.py:31,38` (`"3"` → `3`). The Rust
  implementation must accept both a JSON number and a numeric JSON
  string for `truth_epoch`, falling back to the `-1` sentinel on
  anything else — do not require the property to already be a JSON
  number.
- **Write-side "leave epoch untouched" divergence (accepted, spec-only
  here)**: Python's `_build_node_truth_state_updates`
  (`adapter.py:2192-2215`) only overwrites the `truth_epoch` property
  `if state.get("truth_epoch") is not None`, otherwise the existing
  stored value survives the merge (properties dict is seeded from the
  node's current properties). Because the locked Rust `NodeTruthState`
  has no "unset" epoch on write, the Rust `set_node_truth_state` always
  overwrites both fields — there is no partial-update path. In practice
  this matches Python's only caller: `build.py:257-259` always builds
  `scored[node_id] = {"truth_alignment": coords, "truth_epoch": current_epoch}`
  with both fields present, so no real caller ever
  relies on the None-skip behavior. Note this as an accepted,
  currently-inert divergence — it only matters if a future caller wants
  to update alignment without bumping epoch, which no planned P2-xx task
  does.
- **`truth_alignment` element parsing**: Python takes the property
  as-is `if isinstance(value, (list, tuple))`, otherwise `[]` — it does
  **not** filter or coerce individual elements (a list containing a
  string would pass through as-is into the returned dict, since Python
  is dynamically typed). Rust's `Vec<f64>` is statically typed, so this
  implementation must coerce each element via `.as_f64()`; a note in
  code should say non-numeric array elements are dropped rather than
  causing a parse failure of the whole array (closest faithful analogue
  given the type system difference — acceptable per the "structural
  parity" bar, not bit-identical).
- **IDs schema**: `node_ids` are plain string node ids (not UUIDs
  specifically) — same as `get_node_feedback_weights`/`EdgeKey`, no new
  ID scheme introduced by this task.
- **No `update_edge_property`/edge-scoped truth state**: Python has no
  edge-level `truth_state` method, only node-level — do not add an edge
  variant here (out of scope, unlike feedback weights which do have an
  edge variant).

## Risks & open items

- **Postgres precedent gap**: `PgGraphAdapter` has zero feedback-weight
  overrides today (confirmed: no `feedback_weight` references in
  `pg_graph_adapter.rs`), so this task establishes the *first*
  batch-query override pattern (`get_nodes` + `add_nodes_raw`) for a
  node-scalar property on this backend. Consider a fast-follow to bring
  `get_node_feedback_weights`/`set_node_feedback_weights` up to the same
  pattern on Postgres for consistency — out of scope here, noted only.
- **`-1` sentinel leakage**: any future caller that naively serializes
  `NodeTruthState` to the wire (e.g. a debug endpoint) must not present
  `-1` as a real epoch. Since this task does not add wire exposure, this
  is only a latent risk for whichever task adds the HTTP/CLI surface —
  flag it there.
- **Ladybug write path not batched into a single `UNWIND`**: the spec'd
  Ladybug override reuses the same "loop + in-place `update_node_property`"
  shape as `set_node_feedback_weights` for consistency and lower risk,
  rather than porting Python's single-`UNWIND` write
  (`adapter.py:2217-2232`). This is a performance follow-up, not a
  correctness gap, since Ladybug's `update_node_property` is already an
  in-place merge (no cascade-delete risk).
- **No caller yet**: this task is inert on its own — nothing invokes
  these methods until P2-06 (write) and P2-07 (read) land. Dead-code
  warnings should not fire since the methods are `pub` trait methods,
  but double-check `cargo clippy --all-targets` is clean given no
  internal caller exists yet.
- **`Vec<f64>` element coercion on read**: dropping non-numeric elements
  from a malformed `truth_alignment` array (rather than Python's
  pass-through-as-is) is a structural-parity-only approximation; revisit
  if a cross-SDK test ever needs bit-identical malformed-input handling
  (unlikely, since malformed truth-subspace data should not occur in
  practice — only well-formed writers exist).
