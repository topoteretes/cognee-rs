# P2-01 — Truth-subspace: pure alignment math

**Status:** completed

## Goal

Stand up a new, dependency-light crate `crates/truth-subspace` containing a
faithful Rust port of Python's `cognee/modules/truth_subspace/align.py`
(89 lines, pure functions, no I/O). This is the foundational math layer for
the Phase-2 "truth subspace" re-ranking feature (`use_truth_weight` /
`build_truth_subspace`, both default-off) that later Phase-2 tasks will wire
into `HybridRetriever`. Landing it standalone — with unit tests asserting
Python-computed values — lets the algorithm be verified in isolation before
any retriever, graph, or wire-protocol code depends on it.

## Prerequisites

- None from Phase 1. This task is self-contained: a brand-new crate with no
  dependency on the BM25/HYBRID_COMPLETION wire work, `GraphDBTrait`
  changes, or `DataPoint`/`Data` schema changes. It does not need
  `HybridRetriever`, `SearchType::HybridCompletion`, or the
  `importance_weight` field to exist yet.
- Assumed repo state at the time this task starts: `docs/plans/hybrid-retriever/phase-2/`
  exists but is otherwise empty (this is the first Phase-2 task doc); the
  workspace root `Cargo.toml` `[workspace.members]` list and `sha2 = "0.10"`
  / `hex = "0.4"` workspace dependencies are as currently checked in.
- Downstream (not part of this task, noted for context only): a later
  Phase-2 task will consume `cognee-truth-subspace::align` from
  `cognee-search` to implement the actual truth-weighted re-ranking behind
  `use_truth_weight`/`build_truth_subspace`. That task depends on this one
  landing first, not the other way around.

## Implementation steps

1. **Read the reference exactly once more before coding.** Python source:
   `/tmp/cognee-python/cognee/modules/truth_subspace/align.py` (89 lines).
   Six public functions, all pure, all operating on `Sequence[float]` /
   `Sequence[Sequence[float]]` / `Sequence[object]`. No class state, no
   caching, no async. This maps directly to free functions taking slices.

2. **Scaffold the crate.** Create `crates/truth-subspace/Cargo.toml` modeled
   on the smallest existing leaf crate (`crates/ontology/Cargo.toml` or
   `crates/telemetry/Cargo.toml` for the `[package]` boilerplate shape):
   ```toml
   [package]
   name = "cognee-truth-subspace"
   version.workspace = true
   edition.workspace = true
   rust-version.workspace = true
   license.workspace = true
   description = "Pure truth-subspace alignment math (cosine projection, truth scoring) for cognee's hybrid retriever."
   repository.workspace = true
   homepage.workspace = true
   keywords.workspace = true
   categories.workspace = true
   authors.workspace = true

   [lints]
   workspace = true

   [dependencies]
   sha2 = { workspace = true }
   ```
   No `thiserror` dependency is needed — every function in `align.py` is
   total (never raises), so the Rust port has no fallible paths and no
   error enum. No `serde` dependency either; inputs/outputs are plain
   `f64`/`String`, not wire types (wire-shape structs are a later task's
   concern once this is consumed by `cognee-search`).

3. **Add the crate to the workspace.** Edit root `Cargo.toml`
   `[workspace.members]`, inserting `"crates/truth-subspace"` alongside the
   other `crates/*` entries (keep it near `crates/test-utils` /
   `crates/visualization` in the existing list order, or append before the
   `e2e-cross-sdk`/`bindings-common` comment block — match current list
   ordering, which is roughly pipeline-stage-then-cross-cutting).

4. **Write `src/lib.rs`.** A thin crate root:
   ```rust
   //! Pure truth-subspace alignment math — no I/O, no database access, no
   //! LLM calls. Ported from Python `cognee/modules/truth_subspace/align.py`.
   pub mod align;
   ```
   Add a `#![forbid(unsafe_code)]` or at minimum rely on workspace lints;
   this crate has no unsafe need.

5. **Port `cosine` (align.py:14-30).** Signature:
   `pub fn cosine(a: &[f64], b: &[f64]) -> f64`. Behavior: return `0.0` if
   either slice is empty (align.py:16-17 `if not a or not b`); accumulate
   `dot`, `norm_a`, `norm_b` via a single `zip`-style loop over
   `a.iter().zip(b.iter())` — **note Python's `zip` truncates to the
   shorter sequence** when `a.len() != b.len()`, so use
   `a.iter().zip(b.iter())` (Rust `Iterator::zip` has the same
   shorter-wins truncation semantics — preserve this, do not pad/error on
   length mismatch); return `0.0` if either norm is exactly `0.0`
   (align.py:27-28); else `dot / (norm_a.sqrt() * norm_b.sqrt())`.

6. **Port `node_coords` / `query_coords` (align.py:33-49).** Signatures:
   `pub fn node_coords(node_vec: &[f64], basis_vecs: &[Vec<f64>]) -> Vec<f64>`
   (or `&[&[f64]]` / `&[Vec<f64>]` — prefer `&[Vec<f64>]` for basis storage
   simplicity since callers build the basis once and keep it around; use
   `impl AsRef<[f64]>`-free plain slices, no generics needed for a Phase-2
   internal crate). Body: map `cosine(node_vec, basis_vec)` over every
   `basis_vec` in `basis_vecs`, collect into a `Vec<f64>`. The Python
   zero-pad loop (align.py:42-43) is dead code given `cosine` always
   returns a value per input (never skips) — port it anyway as a defensive
   `while coords.len() < basis_vecs.len() { coords.push(0.0); }` immediately
   after the `map`, to stay byte-for-byte faithful to the Python control
   flow and its comment ("cosine already yields 0.0 per vector... pad
   defensively to keep the contract explicit"). `query_coords` is a direct
   passthrough to `node_coords` (align.py:47-49) — implement as
   `pub fn query_coords(q_vec: &[f64], basis_vecs: &[Vec<f64>]) -> Vec<f64> { node_coords(q_vec, basis_vecs) }`.

7. **Port `truth_score` (align.py:52-74).** Signature:
   `pub fn truth_score(node_coords: &[f64], q_coords: &[f64]) -> f64`.
   Body, in order: (a) return `0.5` (NEUTRAL) if either slice is empty
   (align.py:65-66); (b) compute `weights: Vec<f64> = q_coords.iter().map(|q| q.max(0.0)).collect()`
   — clamp negative query coords to zero (align.py:68); (c)
   `total_weight = weights.iter().sum::<f64>()`; return `0.5` if
   `total_weight == 0.0` (align.py:70-71, no negative-weight query
   contributes); (d) `weighted = node_coords.iter().zip(weights.iter()).map(|(n, w)| n * w).sum::<f64>()`
   — again Python `zip` truncation semantics apply if lengths differ, same
   as step 5; (e) clamp final result to `[0.0, 1.0]`:
   `(weighted / total_weight).clamp(0.0, 1.0)` (align.py:74, Python's
   `max(0.0, min(1.0, ...))` is exactly `f64::clamp`).

8. **Port `truth_factor` (align.py:77-83).** Signature:
   `pub fn truth_factor(node_coords: &[f64], q_coords: &[f64]) -> f64`. Body:
   `0.75 + 0.5 * truth_score(node_coords, q_coords)`. No independent
   neutral-case branch needed — it inherits NEUTRAL 1.0 automatically
   because `truth_score` returns 0.5 in every neutral case (empty/zero
   coords), and `0.75 + 0.5 * 0.5 == 1.0` exactly in `f64`.

9. **Port `stable_signature` (align.py:86-89).** Signature:
   `pub fn stable_signature<T: std::fmt::Display>(ordered_ids: &[T]) -> String`.
   Body: join `ordered_ids.iter().map(|id| id.to_string())` with `"|"`
   (mirrors Python `"|".join(str(item_id) for item_id in ordered_ids)`,
   align.py:88), UTF-8-encode, and hex-digest with `sha2::Sha256` using the
   same `Digest::digest(...)` + `format!("{result:x}")` pattern already
   established in `crates/ingestion/src/content_hasher.rs:29-32` (do not
   add a `hex` crate dependency — the `{:x}` formatter on the `GenericArray`
   digest output already lowercase-hex-encodes it, exactly like the
   existing `ContentHasher::hash_content` `Sha256` arm). Use a generic
   `T: Display` bound rather than `Sequence[object]`'s dynamic typing —
   Rust callers will pass `&[Uuid]` or `&[String]`; `Uuid::to_string()`
   produces the same lowercase-hyphenated form Python's `str(uuid.UUID)`
   produces, so cross-SDK signatures over UUID id lists remain identical
   given identical ordering.

10. **Doc-comment every public function** with the same semantic summary as
    the Python docstring (NEUTRAL-value callouts especially — callers must
    see at a glance that `truth_score`/`truth_factor` degrade gracefully to
    inert values, since that is the mechanism that keeps Phase-2 knobs
    default-off-safe per the overall hybrid-retriever design).

11. **Update `docs/architecture.md`.** Add one line to "Crate breakdown"
    (after `**cognee-utils**` / before `**cognee-test-utils**`, or wherever
    fits the existing loose ordering):
    `**cognee-truth-subspace** — Pure alignment math (cosine projection, query-relevance-weighted truth scoring, stable id signatures) for the Phase-2 hybrid-retriever truth-subspace re-ranking feature. No I/O; consumed by cognee-search once use_truth_weight/build_truth_subspace land.`

12. **Run the build/format/lint loop.** `cargo fmt`, then
    `cargo check --all-targets`, then `cargo test -p cognee-truth-subspace`,
    then the full `scripts/check_all.sh` (fmt-check, check, clippy
    `-D warnings`, and the four binding-check scripts — this crate isn't
    exposed through any binding yet so those scripts should no-op on it,
    but they must still pass overall).

## Parity notes

- **`cosine`** (align.py:14-30): 0.0 on empty-either-input, 0.0 on
  zero-norm-either-input; otherwise standard cosine similarity. No epsilon
  fuzz — exact `== 0.0` float comparison on the computed norm, matching
  Python's `norm_a == 0.0`. Rust: same exact-equality check (`norm_a == 0.0`),
  no `f64::EPSILON` tolerance — this is intentional parity, not a shortcut.
- **Length-mismatch truncation**: neither `cosine` nor `truth_score` guard
  against `a.len() != b.len()`; Python's `zip()` and Rust's
  `Iterator::zip` both silently truncate to the shorter sequence. This is
  preserved deliberately — callers (`node_coords`/`query_coords`) always
  pass matching-length pairs in practice (a vector against one basis vector
  at a time), so the mismatch path is unreachable in normal use but must
  not panic or error if hit.
- **`node_coords`/`query_coords`** (align.py:33-49): output length is
  always `basis_vecs.len()` (the map already guarantees this; the zero-pad
  loop is defensive dead code in both Python and Rust — port it anyway for
  literal parity and because it documents the invariant).
  `query_coords` is a pure alias of `node_coords` — do not duplicate logic,
  call through.
- **`truth_score`** (align.py:52-74): NEUTRAL = `0.5`. Three neutral
  triggers: (1) `node_coords` empty, (2) `q_coords` empty, (3) all
  (clamped) query weights sum to `0.0` (all-zero or all-negative query
  coords). Weighting is **query-relevance-weighted**, not a plain cosine of
  the two coordinate vectors — the Python docstring (align.py:56-60)
  explicitly explains why cosine-of-coords is wrong here (all basis
  cosines are non-negative, so coord vectors share one octant and cosine
  collapses to ~1 regardless of magnitude). This magnitude sensitivity is
  the entire point of the feature (align.py test: `test_truth_score_is_magnitude_sensitive`) —
  do not "simplify" to a cosine call during implementation or review.
  Final clamp to `[0.0, 1.0]` is unconditional even in the non-neutral
  path (handles pathological negative-node-coord inputs).
- **`truth_factor`** (align.py:77-83): `0.75 + 0.5 * truth_score`, range
  `[0.75, 1.25]`, NEUTRAL = `1.0`. This is the actual multiplicative score
  adjustment a later Phase-2 task applies to a retrieval score; this task
  only needs the pure function and its bounds proven by test.
- **`stable_signature`** (align.py:86-89): `sha256(hex)` of
  `"|".join(str(id) for id in ordered_ids)`. Order-sensitive by
  construction (join preserves input order) — `stable_signature([a,b]) != stable_signature([b,a])`.
  Rust `to_string()` on `Uuid` must byte-match Python `str(uuid.UUID(...))`
  (lowercase, hyphenated, e.g. `"3fa85f64-5717-4562-b3fc-2c963f66afa6"`) for
  cross-SDK signature equality — this already holds today (both use the
  canonical RFC 4122 textual form) but call it out since this function's
  entire purpose is cross-run/cross-SDK stability of a derived signature.
- **No behavioral divergence accepted** in this task: every function here
  is pure math with no environment/locale/allocator dependence, so the
  acceptance bar is exact numeric equality (within standard `f64` ULP
  noise via `assert!((a - b).abs() < 1e-9)` / `f64::EPSILON`-scale
  tolerances), not the ~50% structural tolerance used for the BM25/graph
  retrieval acceptance bar elsewhere in this plan — that looser bar applies
  to LLM- and graph-shaped outputs, not to closed-form arithmetic.

## Testing

Add `#[cfg(test)] mod tests` in `crates/truth-subspace/src/align.rs`
(inline unit tests, per project convention), porting every case from
`/tmp/cognee-python/cognee/tests/unit/truth_subspace/test_align.py`
(112 lines) 1:1:

- `cosine`: identical vectors → `1.0`; orthogonal → `0.0`; opposite →
  `-1.0`; scale-invariant (`[1,1]` vs `[2,2]` → `1.0`, use an approx-equal
  assertion); zero vector either side → `0.0`; empty vector either side →
  `0.0`.
- `node_coords`: per-basis-vector projection matches expected values for a
  2D orthonormal basis; zero-padding when node vector is all-zero against
  a 3-vector basis (`len(coords) == len(basis)`, all `0.0`).
- `query_coords`: equals `node_coords` given the same inputs (assert
  literal equality of the two call results).
- `truth_score` neutral cases: empty/empty → `0.5`; zero node & zero query
  → `0.5`; non-zero node but zero query → `0.5`; non-zero node but
  all-negative query (no positive weight) → `0.5`.
- `truth_score` weighted-alignment cases: single-weighted-direction picks
  out the corresponding node coord exactly (`[1,0]`/`[1,0]` → `1.0`;
  `[0.5,0]`/`[1,0]` → `0.5`); equal query weights average the node coords
  (`[0.2,0.8]`/`[0.5,0.5]` → `0.5`).
- `truth_score` magnitude sensitivity: `truth_score([0.4,0.4], q) > truth_score([0.2,0.2], q)`
  for `q = [0.3, 0.3]` — this is the key regression test proving the
  weighted-average approach (not cosine) was ported.
- `truth_factor` neutral: `truth_factor([], [])`, `truth_factor([0.1], [])`,
  `truth_factor([], [0.1])`, and `truth_factor([0.0,0.0],[0.0,0.0])` all
  exactly `1.0`.
- `truth_factor` bounds: four mixed cases all fall within `[0.75, 1.25]`
  inclusive; two extremes hit the bounds exactly (`[1,0]`/`[1,0]` → `1.25`,
  `[0,0]`/`[1,1]` → `0.75`).
- `stable_signature`: same input twice → identical signature, length 64
  (sha256 hex digest length); `stable_signature(["a","b"]) != stable_signature(["b","a"])`
  (order sensitivity).
- One additional Rust-only test not in the Python suite: `stable_signature`
  over `&[Uuid]` produces the same digest as manually constructing the
  `"|"`-joined string of `uuid.to_string()` values and hashing it directly
  — proves the generic `T: Display` path behaves as intended for the
  concrete type Phase-2 retriever code will actually pass.
- No integration tests or e2e-cross-sdk wiring in this task — this crate
  is not yet consumed by anything with I/O, so there is nothing to
  integration-test. Cross-SDK numeric parity (Python-computed vs
  Rust-computed values on shared fixture vectors) is satisfied by porting
  the Python unit test's literal expected values above, which is the
  strongest available parity signal for pure math with no fixtures file.

## Risks & open items

- **No wiring yet**: this crate is inert until a later Phase-2 task
  imports `cognee-truth-subspace::align` from `cognee-search` and connects
  it to `use_truth_weight`/`build_truth_subspace`. Landing it standalone
  is intentional (locked decision: Phase 2 execution deferred but fully
  spec'd) but means CI will not exercise any cross-crate integration for
  this code until that task lands — the risk is purely inline-unit-test
  coverage until then, which is why porting every Python test case
  verbatim matters more than usual.
- **Basis-vector storage type undecided long-term**: step 6 picks
  `&[Vec<f64>]` for `basis_vecs` as the simplest thing that compiles today;
  the eventual truth-subspace-consuming task may prefer `&[&[f64]]` or a
  named `Basis` newtype once it knows how the basis is constructed/cached
  (e.g. from embedding vectors already living behind `Arc` elsewhere).
  Revisit the signature then rather than over-designing it now — the
  function bodies are identical either way. Similarly, `stable_signature`'s
  Python `Sequence[object]` becomes a generic `T: std::fmt::Display` bound
  in Rust rather than a dynamically-typed sequence — fine for the concrete
  `Uuid`/`String` callers expected, but worth a second look if a future
  caller needs a heterogeneous id list.
- **f64 vs Python float**: Python `float` is IEEE-754 binary64, identical
  to Rust `f64` bit-for-bit for the arithmetic used here (`+`, `*`, `/`,
  `sqrt`, comparisons) — no divergence expected, but the test assertions
  should use `f64::EPSILON`-scale tolerances rather than bit-exact
  equality for anything that flows through a `sqrt` (i.e. `cosine`'s
  scale-invariance case) to avoid brittle CI failures across
  platforms/optimization levels, mirroring the Python test's own use of
  `math.isclose(..., rel_tol=1e-9)`.
- **Crate name confirmation**: `cognee-truth-subspace` is the natural name
  under the existing `cognee-<area>` convention; confirm no naming
  collision or preference change before merging the `Cargo.toml` (no
  existing crate or reserved name conflicts as of this writing).
